# 프로젝트 용어집

## 1. 문서 목적

이 문서는 PUBG 환경 사망 집중 지역 분석과 데이터 파이프라인 구현 과정에서
사용하는 용어를 한곳에 정리한다.

용어는 현재 프로젝트의 문맥을 기준으로 설명한다. 일반적인 업계 용어와 프로젝트가
별도로 정한 규칙을 구분하며, 확인되지 않은 내용을 사실처럼 표현하지 않는다.

## 2. 전체 작업 흐름

```text
원본 데이터 확인
→ 데이터 프로파일링
→ 데이터 품질 규칙 정의
→ 정제 및 분석 가능 데이터 생성
→ SQL 지표 생성
→ 결과 저장
→ BI 대시보드와 운영 리포트 제공
```

| 단계 | 핵심 질문 |
|---|---|
| 원본 데이터 확인 | 어떤 파일과 컬럼이 있는가? |
| 프로파일링 | 실제 데이터 상태는 어떠한가? |
| 데이터 품질 | 어떤 값을 분석에 사용할 수 있는가? |
| 정제 | 품질 규칙을 어떻게 적용할 것인가? |
| 분석 | 데이터가 질문에 어떤 답을 주는가? |
| 저장 | 결과와 실행 이력을 어떻게 보존할 것인가? |
| BI | 결과를 어떻게 탐색하고 공유할 것인가? |

## 3. 프로파일링·품질 검사·정제·분석

### 데이터 프로파일링

원본 데이터를 변경하기 전에 데이터의 구조와 상태를 수치로 측정하는 과정이다.

프로파일링에서 확인하는 대표 항목:

- 파일 수와 전체 행 수
- 컬럼 이름과 데이터 타입
- NULL과 빈 문자열 수
- 고유값과 값의 분포
- 숫자의 최솟값과 최댓값
- 중복 후보
- 테이블 간 연결률
- 데이터 기간

현재 프로젝트의 프로파일링 사례:

```text
killed_by 결측: 0건
map 결측: 783,392건
피해자 좌표 0,0: 2,958,383건
Falling: 708,367건
Drown: 271,712건
```

프로파일링은 상태를 측정할 뿐, 그 값을 자동으로 삭제하거나 품질 실패로 확정하지
않는다.

### 데이터 품질 검사

분석 목적에 따라 데이터가 사용 조건을 만족하는지 판정하는 과정이다.

```text
프로파일링:
0,0 좌표가 2,958,383건이라고 측정

품질 규칙:
0,0 좌표는 공간 분석에서 사용하지 않음
```

동일한 행도 분석 목적에 따라 사용 가능 여부가 달라질 수 있다.

```text
좌표가 없는 Falling 행:
전체 Falling 건수에는 사용 가능
위치 히트맵에는 사용 불가
```

### 데이터 정제

정의한 품질 규칙을 실제 처리 과정에 적용하는 작업이다.

정제는 원본 파일을 직접 수정한다는 의미가 아니다. 원본은 보존하고 정제된 뷰,
테이블 또는 파일을 별도로 생성한다.

정제 작업의 예:

- 문자열 앞뒤 공백 제거
- 원인 이름 표준화
- 분석 불가능한 위치 제외
- 잘못된 타입을 안전하게 변환
- 제외 사유 기록
- 분석 가능한 행만 별도 테이블로 생성

### 데이터 분석

정제된 데이터와 지표를 이용해 문제 정의에 답하는 과정이다.

현재 프로젝트의 분석 질문:

> 에란겔과 미라마에서 `Falling`과 `Drown` 사망이 특정 위치에 여러 경기와
> 날짜에 걸쳐 반복적으로 집중되는가?

### 네 단계의 차이

| 구분 | 예시 |
|---|---|
| 프로파일링 | Drown의 60.40%가 `0,0`이라고 측정 |
| 품질 규칙 | `0,0`을 공간 분석 불가 위치로 분류 |
| 정제 | `0,0`을 히트맵 입력에서 제외하고 건수 기록 |
| 분석 | 반복되는 익사 집중 위치 후보 탐지 |

## 4. 데이터 구조 용어

### 데이터셋

특정 목적을 위해 모인 파일 또는 테이블의 집합이다.

현재 사용하는 데이터셋:

```text
PUBG Match Deaths and Statistics
Kaggle identifier: skihikingkevin/pubg-match-deaths
```

### 원본 데이터

제공자로부터 받은 뒤 내용 값을 변경하지 않은 데이터다. 현재 프로젝트에서는
압축 해제한 CSV를 원본 입력으로 취급한다.

### 행

테이블의 한 레코드다. deaths CSV의 한 행은 사망 이벤트 후보를 나타낸다.

### 컬럼

행을 구성하는 속성이다. 예를 들어 `killed_by`는 사망 원인,
`victim_position_x`는 피해자 X 좌표다.

### 스키마

컬럼 이름, 데이터 타입, 필수 여부, 의미와 관계를 정의한 구조다.

### 데이터 타입

값이 문자열, 정수, 실수, 날짜 등 어떤 형태로 저장되는지를 의미한다.

### Grain

테이블의 한 행이 무엇을 나타내는지를 의미한다. 한국어로는 분석 단위 또는 행의
단위라고 표현할 수 있다.

예시:

```text
deaths grain 후보: 한 사망 이벤트
aggregate grain 후보: 한 경기의 한 플레이어
hotspot metric grain: 한 맵의 한 위치 격자와 한 사망 원인
```

중복 검사를 완료하기 전에는 grain을 최종 확정하지 않는다.

### 키

행이나 개체를 식별하거나 테이블을 연결하는 컬럼이다.

현재 주요 키:

```text
match_id: 경기 식별 및 deaths와 aggregate 연결
```

### 후보 키

행을 고유하게 식별할 가능성이 있어 검증이 필요한 컬럼 조합이다.

### NULL

값이 존재하지 않음을 데이터베이스가 표현하는 방식이다.

`NULL`은 숫자 `0`, 문자열 `'NULL'`, 빈 문자열 `''`과 다르다.

### 행 결측과 경기 단위 결측

특정 행의 값이 NULL이어도 같은 `match_id`의 다른 행에 값이 있으면 기존
값으로 연결할 가능성이 있다. 반면 같은 경기의 모든 행이 NULL이면 경기
내부에서는 복구할 수 없다.

현재 `map` NULL 783,392행은 8,893개 경기에 속하며, 해당 경기의 모든
deaths 행에서 `map`이 NULL이었다. 따라서 에란겔이나 미라마로 추정하지 않고
맵별 공간 분석에서 `MISSING_MAP`으로 제외한다.

```text
맵이 필요 없는 전체 원인 건수: 사용 가능
맵별 집계와 공간 히트맵: 사용 불가
```

### 빈 문자열

문자열의 길이가 0인 값이다.

```text
''
```

공백만 들어 있는 문자열도 별도로 확인해야 한다.

### Sentinel Value

결측이나 특수 상태를 나타내기 위해 실제 값 대신 사용하는 특정 값이다.

현재 데이터의 `0,0` 좌표가 sentinel value인지 제공자 문서에서 확정되지는 않았다.
다만 실제 위치로 해석하기 어려운 사례가 있어 위치 미제공 또는 비정상 값 후보로
관리한다.

### `0,0` 좌표

X와 Y가 모두 숫자 0인 위치다. SQL의 NULL과 다르다.

공식 PUBG 좌표 체계에서 `0,0`은 맵의 왼쪽 위 원점이다. 그러나 현재 데이터에서는
주먹 공격처럼 실제 위치로 해석하기 어려운 사건에도 `0,0`이 기록되어 있다.

현재 환경 사망 공간 분석의 확정 규칙:

```text
전체 사망 건수: 포함 가능
공간 히트맵: 제외
제외 사유: INVALID_OR_UNAVAILABLE_POSITION
```

`Drown` 271,712행 중 164,124행이 정확한 `0,0`이었고, 원점 10m
이내에는 이를 제외한 비영점 `Drown`이 없었다. 따라서 현재 분석에서는
실제 원점 위치가 아니라 위치 미제공 또는 특수 상태 후보로 처리한다.

이 규칙은 `0,0`의 발생 원인을 접속 종료, 잠수 플레이 또는 게임 오류로
확정한다는 뜻이 아니다.

## 5. 데이터 품질 차원

### 완전성

필수 값이 NULL이나 빈 문자열 없이 존재하는 정도다.

예시:

```text
map completeness
= map이 존재하는 행 수 / 전체 행 수
```

### 유효성

값이 정한 형식과 허용 범위를 만족하는 정도다.

예시:

- 좌표가 숫자로 변환되는가?
- 좌표가 맵의 허용 범위 안에 있는가?
- `map`이 정의된 값인가?

### 일관성

관련된 값들이 서로 모순되지 않는 정도다.

예시:

- 한 `match_id`가 하나의 맵을 가지는가?
- 한 `match_id`가 하나의 경기 날짜를 가지는가?

### 고유성

고유해야 하는 행이나 키가 중복되지 않는 정도다.

### 완전 중복

한 행의 모든 원본 컬럼 값이 다른 행과 완전히 같은 경우다.

```text
행 A: match_id=M1, victim=P1, time=170, killed_by=Drown, x=0, y=0
행 B: match_id=M1, victim=P1, time=170, killed_by=Drown, x=0, y=0
```

두 행의 모든 값이 같다면 같은 원본 레코드가 파일 또는 배치에 중복 저장됐을
가능성이 있다. 현재 deaths에서는 12개 원본 컬럼 전체와 원본 파일 위치를
구분해 파일 내부 중복과 파일 간 중복을 각각 측정해야 한다.

### 사망 이벤트 중복 후보

모든 컬럼이 같지는 않지만 같은 실제 사망 사건을 나타낼 가능성이 있는 행
조합이다.

```text
같은 match_id
+ 같은 victim_name
+ 같은 time
+ 같은 killed_by
```

예를 들어 위 값은 같지만 placement 또는 좌표 표현이 조금 다르면 완전
중복은 아니어도 같은 사망 사건이 두 번 기록된 후보가 될 수 있다.

`match_id + victim_name + time`은 아직 확정 키가 아니라 검증할 후보 키다.
같은 조합에 여러 행이 발견되면 `killed_by`, 좌표, killer 정보까지 비교해
실제로 하나의 사건인지 판단한다.

같은 위치에서 같은 원인으로 여러 사람이 사망했다는 이유만으로 중복 처리하지
않는다. 서로 다른 피해자 또는 서로 다른 경기라면 별개의 사건이다.

중복을 확인하는 이유:

- 같은 사망을 두 번 세어 위치별 사망 건수가 부풀려지는 것을 방지한다.
- 원본 파일 분할이나 재처리 과정에서 같은 행이 다시 들어왔는지 확인한다.
- 제거한 중복 수와 적용한 판단 키를 실행 이력에 남긴다.

완전 중복은 원본을 보존한 상태에서 분석용 데이터의 중복 제거 후보가 된다.
사망 이벤트 중복 후보는 자동 삭제하지 않고 상세 컬럼을 비교한 뒤 규칙을
확정한다.

### 원본 중복과 파이프라인 중복

중복이 발견됐다고 해서 현재 프로젝트의 파이프라인이 만들었다고 바로 판단하지
않는다. 중복이 어느 단계에서 처음 나타났는지 구분해야 한다.

```text
원본 중복:
다운로드한 CSV에 같은 사건이 이미 여러 번 존재

파이프라인 중복:
원본에는 한 번만 있지만 처리·조인·적재 과정에서 여러 행으로 증가
```

파이프라인 중복의 대표적인 원인:

- 같은 입력 파일 또는 배치를 두 번 처리
- 재실행할 때 기존 결과에 다시 추가
- 일대다 관계를 고려하지 않은 조인으로 행이 증가
- 잘못된 이벤트 키로 서로 다른 데이터를 중복 저장

현재 aggregate는 한 경기의 여러 플레이어 행을 가지므로 같은 `match_id`가
반복되는 것이 정상이다. deaths도 한 경기에서 여러 사망이 발생하므로
`match_id`만 같다고 중복이 아니다.

특히 deaths를 플레이어 단위 aggregate와 `match_id`만으로 바로 조인하면 한
사망 행이 경기 참가자 수만큼 증가하는 Join Explosion이 발생할 수 있다.
날짜를 연결할 때 경기당 한 행인 `dim_match`를 먼저 만드는 이유가 이것이다.

중복 발생 단계를 구분하는 방법:

1. 원본 CSV에서 완전 중복과 이벤트 중복 후보를 측정한다.
2. 정제 전후의 입력·출력·중복 제외 행 수를 대조한다.
3. 조인 전후 행 수와 키별 행 수를 비교한다.
4. 같은 `batch_id`를 재실행해 결과 행 수가 증가하지 않는지 확인한다.

원본 중복 측정값은 파이프라인 입력 기준선이 된다. 원본보다 처리 결과에서
설명되지 않은 중복이 늘어나면 파이프라인 오류로 판단할 근거가 된다.

현재 deaths 전체 측정 결과:

```text
완전 중복 그룹: 193
중복 그룹에 포함된 행: 404
한 행만 남길 때의 초과 행: 211
파일 간 중복 그룹: 0
```

따라서 원본에는 완전 중복이 존재하지만 전체의 약 0.000323%로 매우 작다.
원본은 보존하고 분석용 출력에서 완전히 같은 추가 행만 제외한다.

`match_id + victim_name + time + killed_by` 기준 이벤트 후보는 2,652개
그룹이었지만, 이 중 2,470개 그룹은 다른 상세값을 가지고 있었다. 이들은
완전 중복이 아니므로 자동 삭제하지 않는다.

### 중복 품질 검사의 역할 경계

중복 검사는 데이터 분석가와 데이터 엔지니어 중 한 직군만의 업무로 고정되지
않으며 조직 구조에 따라 공동으로 수행한다.

데이터 분석가 또는 Analytics Operation이 담당할 수 있는 범위:

- 분석 테이블의 grain과 중복 판정 기준 정의
- SQL로 중복 규모와 지표 영향을 측정
- 조인 전후 행 수와 집계값 검증
- 품질 이상을 리포트하고 대시보드 게시 여부 판단
- 재현 가능한 검사 쿼리와 품질 규칙 관리

Analytics Engineer 또는 Data Engineer가 주로 담당하는 범위:

- 원본 수집과 적재 과정의 중복 발생 원인 수정
- 배치 재실행과 멱등성 구현
- 대규모 변환·조인 파이프라인 최적화
- 저장소 제약 조건과 운영 복구 절차 구현

분석가는 파이프라인 인프라 전체를 반드시 직접 구축할 필요는 없지만, 자신이
제공하는 지표가 중복으로 왜곡되지 않았는지는 확인할 책임이 있다. 현재
프로젝트에서는 수집 플랫폼을 새로 만드는 대신 Python과 SQL로 중복을 측정하고,
분석 사용 규칙과 실행 이력을 자동화하는 범위까지만 다룬다.

### 정확성

값이 실제 게임에서 발생한 사실과 일치하는 정도다. 공개 CSV만으로는 모든 정확성을
직접 확인할 수 없으므로 다른 컬럼과 공식 문서를 이용해 모순을 찾는다.

### 참조 무결성

한 테이블의 키가 연결 대상 테이블에도 존재하는지를 의미한다.

예시:

```text
deaths.match_id가 aggregate.match_id에 존재하는가?
```

### 연결률

조인 조건을 만족해 다른 테이블과 연결된 행의 비율이다.

현재 측정값:

```text
deaths 날짜 연결률: 약 99.996%
연결 실패: 2,609행
```

### 데이터 커버리지

질문에 필요한 값이 실제로 제공되는 범위다.

현재 공간 분석의 임시 커버리지:

```text
Falling의 맵·비영점 좌표 커버리지: 약 97.00%
Drown의 맵·비영점 좌표 커버리지: 약 39.11%
```

커버리지가 낮으면 분석 결과가 전체 사건을 대표하지 못할 수 있다.

### 분석 적격 행

현재 분석 질문에 필요한 모든 품질 조건을 만족해 최종 지표에 사용할 수 있는
행이다.

현재 환경 사망 분석 조건:

```text
killed_by가 Falling 또는 Drown
+ 완전 중복의 대표 한 행
+ map이 ERANGEL 또는 MIRAMAR
+ 피해자 좌표가 0,0이 아님
+ 피해자 좌표가 공식 맵 범위 안
+ 기존 aggregate 날짜가 match_id로 연결됨
```

전체 환경 사망 980,079행 중 현재 분석 적격 행은 793,356행이다.

### 제외 사유 중복

한 행이 `MISSING_MAP`과 `0,0`을 동시에 만족하는 것처럼 여러 품질 규칙에
해당하는 상태다. 규칙별 실패 건수를 단순히 더하면 같은 행을 여러 번 세게 된다.

현재 프로젝트는 모든 제외 사유를 보존하면서 건수 대조를 위해 대표 사유 하나도
정한다.

```text
원본
= 완전 중복 초과
+ 중복 제거 후 고유 제외
+ 최종 분석 적격
```

현재 대조 결과는 `980,079 = 65 + 186,658 + 793,356`이며 차이는 0이다.

### 격리

품질 규칙을 통과하지 못한 행을 조용히 삭제하지 않고 별도로 보존하는 처리다.

격리 시 기록할 항목:

- 원본 행 식별 정보
- 실패한 규칙
- 제외 사유
- 실행 ID
- 처리 시각

## 6. SQL과 집계 용어

### SQL

테이블 형태의 데이터를 조회, 필터링, 연결하고 집계하는 언어다.

### Query

SQL로 작성한 하나의 데이터 요청이다.

### SELECT

조회할 컬럼이나 계산값을 지정한다.

### WHERE

조회할 행의 조건을 지정한다.

### GROUP BY

같은 값을 가진 행을 그룹으로 묶어 집계한다.

### 집계

여러 행을 합쳐 개수, 합계, 평균, 최솟값, 최댓값 등의 요약값을 만드는 작업이다.

### COUNT

행이나 값의 개수를 계산한다.

```sql
COUNT(*)
```

### COUNT DISTINCT

중복을 제거한 고유값 수를 계산한다.

```sql
COUNT(DISTINCT match_id)
```

### Join

공통 키를 이용해 두 데이터셋의 컬럼을 연결하는 작업이다.

현재 프로젝트의 예:

```text
deaths.match_id = aggregate.match_id
```

### INNER JOIN

양쪽 데이터에 모두 존재하는 키만 결과에 포함한다.

### LEFT JOIN

왼쪽 데이터의 모든 행을 유지하고 오른쪽에서 연결되는 값만 추가한다. 연결 실패를
측정할 때 유용하다.

### Join Explosion

양쪽 테이블에 같은 키가 여러 번 존재할 때 의도보다 많은 행이 생성되는 문제다.

aggregate는 한 `match_id`에 여러 플레이어 행이 있으므로 deaths와 바로 조인하면
행이 폭증할 수 있다. 날짜 연결 전에는 경기당 한 행인 `dim_match`를 만들어야 한다.

### Dimension Table

분석 대상에 대한 기준 속성을 한 행으로 정리한 테이블이다.

현재 프로젝트의 `dim_match` 후보:

```text
match_id
date
```

### Numerator

비율에서 위에 놓이는 관심 사건 수다.

예시:

```text
특정 격자의 Falling 사망 수
```

### Denominator

비율에서 전체 규모를 나타내는 기준값이다.

예시:

```text
전체 경기 수
해당 격자의 전체 사망 수
```

분모가 달라지면 지표의 의미도 달라진다.

### Rate

분자와 분모를 이용해 규모 차이를 보정한 값이다.

```text
경기 1,000건당 Falling 사망
= Falling 사망 수 / 고유 경기 수 * 1,000
```

## 7. 현재 분석 용어

### 사망 이벤트

플레이어가 특정 원인으로 사망한 것으로 기록된 사건이다.

### 사망 원인

`killed_by` 컬럼에 기록된 사망을 발생시킨 원인이다.

### 환경 사망

현재 프로젝트가 분석 목적으로 정의한 분류다.

초기 환경 사망:

```text
Falling
Drown
```

이 분류는 PUBG가 공식적으로 정한 전체 환경 사망 분류라고 주장하지 않는다.

### 공간 분석

사건의 X·Y 좌표를 이용해 위치별 분포와 반복성을 확인하는 분석이다.

### 위치 격자

연속적인 X·Y 좌표를 일정한 크기의 구간으로 나눈 공간 단위다.

```text
map_grid_id = map + x_grid + y_grid
```

격자 크기는 좌표 분포와 맵 좌표 체계를 확인한 뒤 정한다.

### Hotspot

관심 사건이 상대적으로 많이 또는 반복적으로 관측된 위치다.

현재 프로젝트에서는 다음 조건을 함께 고려한다.

- 환경 사망 건수
- 고유 경기 수
- 발생 날짜 수
- 위치 내 환경 사망 비율

핫스팟은 버그가 확인된 위치나 실제 사망 확률이 높은 위치와 같은 의미가 아니다.

### 반복성

같은 현상이 한 경기나 하루에만 발생하지 않고 여러 경기와 날짜에서 다시 관측되는
정도다.

### 집중도

전체 사건 중 일부 위치가 차지하는 비율 또는 위치별 사건 분포의 편중 정도다.

### 노출

플레이어가 특정 위험이나 위치를 경험할 기회가 있었던 정도다.

현재 데이터에는 위치별 방문자 수와 이동 경로가 없어 정확한 공간 노출을 계산할 수
없다.

### 사망 집중 지역과 위험 지역

```text
사망 집중 지역:
사망 사건이 많이 관측된 위치

위험 지역:
방문한 플레이어 대비 사망 확률이 높은 위치
```

현재 데이터로는 사망 집중 지역을 찾을 수 있지만 정확한 위험 지역은 확정할 수 없다.

### QA 점검 후보

분석 결과를 바탕으로 사람이 지형, 이동 동선, 충돌 또는 환경 오브젝트를 추가로
확인할 필요가 있는 위치다.

QA 점검 후보는 버그 확정이나 수정 지시가 아니다.

### AFK-like Pattern

이동 거리와 활동이 매우 적어 잠수 플레이와 비슷하게 보이는 데이터 패턴이다.

실제 키 입력이나 이동 경로가 없으면 잠수 플레이를 확정할 수 없으므로
`AFK`가 아니라 `AFK-like`로 표현한다.

## 8. 파일과 저장 형식

### CSV

쉼표로 값을 구분한 텍스트 파일이다. 확인과 교환은 쉽지만 데이터 타입 정보가
없고 대용량 반복 조회 효율이 낮을 수 있다.

### Parquet

컬럼 단위로 저장하는 파일 형식이다. 필요한 컬럼만 읽기 쉽고 압축과 대용량 분석에
유리하다.

현재 프로젝트에서는 먼저 CSV 기준 처리 시간과 크기를 측정한 뒤 Parquet의 효과를
비교한다.

### DuckDB

CSV와 Parquet를 직접 SQL로 조회할 수 있는 분석용 데이터베이스 엔진이다.

현재 역할:

- 대용량 CSV 프로파일링
- 데이터 품질 집계
- 정제와 변환
- SQL 지표 생성

### PostgreSQL

품질 결과, 실행 이력, 집계 테이블을 저장하는 데이터베이스다. 전체 원본 CSV는
PostgreSQL에 적재하지 않는다.

### Superset

PostgreSQL 등에 저장된 분석 결과를 표, 차트, 필터와 대시보드로 제공하는 BI 도구다.

Superset이 원본 데이터 품질을 자동으로 보장하지는 않는다.

## 9. 파이프라인 운영 용어

### 데이터 파이프라인

데이터 입력부터 검사, 정제, 집계, 저장과 제공까지 이어지는 반복 가능한 처리
과정이다.

### Batch

한 번의 파이프라인 실행에서 함께 처리하는 데이터 묶음이다.

### Run ID

각 파이프라인 실행을 구분하는 고유 식별자다.

### 실행 이력

파이프라인을 언제 어떤 입력으로 실행했고 어떤 결과가 나왔는지 기록한 정보다.

필수 기록 항목:

- 입력 행 수
- 출력 행 수
- 제외 또는 실패 행 수
- 실행 시간
- 실행 상태
- 오류 메시지

### Idempotency

동일한 배치를 다시 실행해도 결과가 중복되거나 달라지지 않는 성질이다.

### Baseline

향후 실행 결과와 비교하기 위해 정한 기준 데이터 상태다.

현재 1차 프로파일링 결과는 이후 배치의 행 수, 결측률과 값 분포를 비교하는 초기
baseline이 될 수 있다.

### Data Drift

시간이 지나면서 값의 분포나 구성 비율이 달라지는 현상이다.

### Schema Drift

컬럼의 추가·삭제, 이름 변경 또는 데이터 타입 변경처럼 데이터 구조가 달라지는
현상이다.

### Anomaly

평소의 범위나 명시적인 규칙에서 벗어난 값 또는 실행 결과다.

이상값이 반드시 오류라는 의미는 아니다. 추가 확인이 필요한 신호다.

## 10. BI와 지표 용어

### BI

Business Intelligence의 약자로, 분석 결과를 탐색하고 의사결정에 활용할 수 있도록
표와 차트, 대시보드로 제공하는 영역이다.

### Metric

데이터로 계산한 측정값이다.

예시:

- 환경 사망 수
- 고유 경기 수
- 좌표 커버리지
- 연결 실패율

### KPI

중요한 목표의 달성 여부를 판단하기 위해 선택한 핵심 지표다. 모든 metric이 KPI는
아니다.

### Dashboard

여러 지표와 차트를 한 화면에서 탐색하고 모니터링할 수 있도록 구성한 화면이다.

### Heatmap

위치별 값의 크기를 색의 강도로 표현한 지도 또는 격자 시각화다.

## 11. 사실·추정·규칙·결론 구분

### 확인된 사실

실제 데이터나 공식 문서에서 확인한 내용이다.

```text
Drown 271,712건 중 164,124건의 좌표가 0,0이다.
```

### 추정 또는 가설

확인된 사실을 설명하기 위해 제시하지만 아직 증명되지 않은 내용이다.

```text
0,0은 위치가 정상적으로 수집되지 않았을 가능성이 있다.
```

### 데이터 품질 규칙

분석 목적과 확인된 근거를 이용해 프로젝트가 정한 사용 기준이다.

```text
0,0은 공간 히트맵에서 제외하고 제외 건수를 기록한다.
```

### 분석 결론

정의한 지표와 품질 규칙을 적용한 뒤 데이터에서 얻은 답이다.

```text
여러 경기와 날짜에 걸쳐 반복된 Falling 집중 위치를 탐지했다.
```

분석을 실행하기 전에는 결론을 완료된 사실처럼 작성하지 않는다.

## 12. STAR 용어

### STAR

경험을 상황, 과제, 행동, 결과 순서로 설명하는 방법이다.

### Situation

행동하기 전 어떤 상황과 문제가 있었는지 설명한다.

현재 프로젝트 초안:

> PUBG 공개 데이터에는 에란겔과 미라마의 사망 원인과 피해자 위치가 포함되어
> 있었지만, 환경 사망이 특정 위치에 반복적으로 집중되는지를 보여주는 집계
> 지표는 제공되지 않았다.

### Task

해당 상황에서 해결해야 했던 구체적인 목표와 책임을 설명한다.

현재 프로젝트 초안:

> 여러 경기와 날짜에서 반복되는 환경 사망 집중 지역을 재현 가능한 지표로
> 탐지한다.

### Action

목표를 달성하기 위해 직접 수행한 작업과 판단을 설명한다.

현재 수행한 Action:

- 필요한 컬럼 선정
- DuckDB 기반 전체 deaths 프로파일러 구현
- 65,370,475행의 결측과 좌표 분포 측정
- `0,0`과 낮은 Drown 좌표 커버리지 발견

### Result

행동으로 얻은 측정 가능한 결과와 영향이다.

최종 Result는 아직 작성하지 않는다. 핫스팟 분석, 품질 통과 행 수, 실행 시간,
대시보드 결과를 실제로 측정한 뒤 기록한다.

## 13. 도구별 역할 요약

| 도구 | 프로젝트 역할 |
|---|---|
| Python | SQL 실행, 반복 처리, 오류 처리와 실행 이력 자동화 |
| DuckDB | 대용량 CSV·Parquet 조회, 프로파일링, 정제와 집계 |
| SQL | 필터, 조인, 집계와 지표 계산 |
| Parquet | 정제된 대용량 상세 데이터 저장 후보 |
| PostgreSQL | 품질 결과, 실행 이력과 집계 테이블 저장 |
| Superset | 분석 결과 대시보드와 탐색 화면 |
| pytest | 데이터 품질 규칙과 핵심 함수 테스트 |
| Ruff | Python 코드 스타일과 정적 검사 |
| LLM | 계산 결과를 운영 리포트 문장으로 요약 |

LLM은 수치 계산이나 최종 데이터 품질 판정에 사용하지 않는다.

## 14. 이상 행동 탐지 용어

### 의심 행동 후보

명시적인 규칙이나 일반적인 분포에서 반복적으로 벗어나 추가 확인이 필요한
플레이어 행동이다.

의심 행동 후보는 핵 사용이 확인된 사용자와 같은 의미가 아니다.

### 핵 사용자 확정

운영자가 충분한 로그, 탐지 시스템, 신고, 영상과 제재 근거를 종합해 불법
프로그램 사용을 확인한 상태를 의미한다.

현재 공개 데이터에는 이러한 확정 라벨이 없으므로 프로젝트 결과로 사용할 수 없는
표현이다.

### False Positive

정상 행동을 비정상 또는 부정행위로 잘못 탐지한 경우다. 한국어로 오탐이라고 한다.

좌표 `0,0`과 같은 품질 문제를 제거하지 않고 킬 거리를 계산하면 오탐이 크게
증가할 수 있다.

### Behavioral Signal

비정상 행동 가능성을 나타내지만 단독으로 결론을 내릴 수 없는 측정값이다.

예시:

- 무기 분포에서 크게 벗어난 킬 거리
- 여러 경기에서 반복된 극단 거리 킬
- 짧은 시간 구간의 비정상적인 킬 집중

### Anonymization

사용자 이름이나 계정 식별자를 원래 값으로 되돌리기 어렵게 변환하거나 제거하는
과정이다. 의심 행동 후보를 분석하더라도 포트폴리오와 대시보드에는 원본 사용자
이름을 공개하지 않는다.

## 15. 원본 컬럼과 파생 컬럼

### 원본 컬럼

제공받은 파일에 처음부터 들어 있는 컬럼이다.

현재 데이터에서 `date`는 aggregate CSV의 원본 컬럼이다.

```text
aggregate.date: 존재
deaths.date: 존재하지 않음
```

### 파생 컬럼

원본 컬럼을 계산하거나 다른 테이블에서 연결해 새로 만든 컬럼이다.

death 이벤트 관점에서 날짜는 deaths에 직접 존재하지 않으므로 aggregate에서
`match_id`로 연결한 파생 컬럼이다. 분석 테이블에서는 출처를 명확히 하기 위해
`match_date`라는 이름을 사용할 수 있다.

```text
deaths.match_id
→ dim_match.match_id와 연결
→ dim_match.match_date 추가
```

### `date`와 `match_date`

| 이름 | 위치 | 의미 |
|---|---|---|
| `date` | aggregate 원본 | 해당 경기의 기록 시각 |
| `match_date` | death 분석용 파생 테이블 | aggregate의 `date`를 경기 단위로 연결한 값 |

aggregate는 한 경기에 여러 플레이어 행이 있으므로 deaths와 바로 조인하면 행이
증가할 수 있다. 먼저 경기당 한 행인 `dim_match`를 만들어야 한다.

```text
aggregate
→ match_id별 date 고유성 검사
→ 경기당 한 행의 dim_match 생성
→ deaths와 LEFT JOIN
```

현재 프로파일링에서 한 `match_id`가 여러 aggregate 날짜를 가진 경우는 0건이었다.
death 행 65,370,475건 중 65,367,866건에 날짜가 연결됐고 2,609건은 연결되지 않았다.

### 날짜 값 생성 금지 원칙

여기서 `match_date`가 파생 컬럼이라는 표현은 새로운 날짜 값을 추정하거나
생성한다는 뜻이 아니다. 다음 조건을 모두 만족할 때 기존
`aggregate.date` 값을 이름만 바꾸어 사용한다.

- death 행과 aggregate 경기의 `match_id`가 정확히 일치한다.
- 해당 `match_id`에 연결된 `aggregate.date` 고유값이 하나다.

현재 날짜 입력, 파일명 기반 추정, 인접 경기 날짜 사용, 보간, 임의의
최솟값 또는 최댓값 선택은 허용하지 않는다. 정확히 연결되지 않은 행의
`match_date`는 `NULL`로 유지하고 날짜 기반 분석에서 제외하며, 제외 사유와
건수는 데이터 품질 결과에 기록한다.
