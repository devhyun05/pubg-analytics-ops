# AI 운영 보고서 자동화

> 문서 상태: 초기 설계
>
> 구현 상태: 미구현
>
> AI 역할: 확정 결과의 요약과 전달 문구 작성

## 1. 목적

이 단계는 반복적으로 확인해야 하는 파이프라인 실행 결과, 품질 실패, 지표 이상과 스키마 변화를 운영 보고서 초안으로 정리한다.

AI는 수치를 계산하거나 데이터 정상 여부를 최종 결정하지 않는다. Python과 SQL이 확정한 구조화된 결과만 입력받아 사람이 검토하기 쉬운 설명과 점검 우선순위를 작성한다.

## 2. 입력

이 단계는 [06_RESULT_STORAGE.md](06_RESULT_STORAGE.md)에 저장된 결과를 입력으로 받는다.

- 품질 검사 결과
- 지표 이상 변화
- 입력·출력·실패 행 수
- 파이프라인 실행 성공·실패 상태
- 실패 단계와 구조화된 오류
- 스키마 변화
- 마지막 정상 갱신 시각
- 현재 `run_id`와 비교 대상 `run_id`

원본 CSV, 전체 Parquet, 플레이어별 상세 기록은 LLM 입력으로 보내지 않는다.

## 3. 처리

### 입력 페이로드 생성

Python은 PostgreSQL에서 확정 결과를 조회해 제한된 구조화 페이로드를 만든다.

예정 항목은 다음과 같다.

| 항목 | 내용 |
|---|---|
| 실행 요약 | 실행 상태, 시작·종료 시각, 소요 시간 |
| 처리량 | 입력·출력·실패 행 수 |
| 품질 | 상태별 검사 수, 실패·경고 규칙 |
| 이상 변화 | 이전 정상 배치 대비 변화량과 기준 |
| 스키마 | 추가·삭제·타입 변경 요약 |
| 최신성 | 마지막 정상 게시 시각 |
| 근거 식별자 | `run_id`, 규칙 및 지표 버전 |

수치와 상태는 프롬프트에서 다시 계산하지 않고 입력값을 그대로 사용한다.

### AI 역할

AI의 역할은 다음으로 제한한다.

- 일일 또는 실행 단위 운영 보고서 초안
- 실패한 품질 검사 요약
- 지표 이상 변화에 대한 읽기 쉬운 설명
- 확인이 필요한 항목의 우선순위 정리
- Slack 전달 문구 초안
- Jira 이슈 설명 초안

AI 출력은 제안 또는 초안이며 담당자의 최종 확인 전 자동 전송하지 않는다.

### 출력 제한

- 입력에 없는 원인을 사실처럼 단정하지 않는다.
- 품질 상태를 변경하지 않는다.
- 입력 수치를 새로 계산하거나 보정하지 않는다.
- 오류 상세에 없는 해결책을 완료된 조치로 표현하지 않는다.
- 플레이어 식별 정보나 비밀값을 포함하지 않는다.
- KRAFTON, PUBG 또는 OP.GG의 공식 보고서처럼 표현하지 않는다.

### 규칙 기반 대체 보고서

LLM 호출이 실패해도 다음 형식의 보고서를 생성한다.

```text
실행 ID:
실행 상태:
입력 행 수:
출력 행 수:
실패 행 수:
품질 상태:
실패 검사:
경고 검사:
스키마 변화:
마지막 정상 갱신:
점검 필요 항목:
```

대체 보고서는 템플릿과 구조화된 입력값만 사용한다.

### 생성 이력

다음 항목을 저장한다.

- 보고서 실행 식별자
- 기준 `run_id`
- 생성 방식 `llm` 또는 `fallback`
- 모델 또는 템플릿 버전
- 생성 시작·종료 시각
- 성공·실패 상태
- 오류 유형
- 입력 토큰 및 비용 정보
- 사람 검토 상태

비밀값, 전체 프롬프트의 민감 데이터, 인증 정보는 저장하지 않는다.

## 4. 출력

이 단계의 출력은 다음과 같다.

- 운영 보고서 초안
- 품질 실패 및 경고 요약
- 점검 우선순위 목록
- Slack 전달 문구 초안
- Jira 이슈 설명 초안
- LLM 또는 대체 보고서 생성 이력

이 출력은 사람이 검토한 뒤 운영 커뮤니케이션에 사용한다. 자동 Slack 전송이나 Jira 이슈 생성은 현재 기본 범위에 포함하지 않는다.

## 5. 사용 기술

- Python 3.12
- PostgreSQL
- 구조화된 JSON 입력
- LLM API 또는 로컬 모델 후보
- 규칙 기반 템플릿
- 환경변수 기반 비밀값 관리

LLM 제공자와 SDK는 확정되지 않았다. 새로운 의존성이나 외부 API를 추가하기 전에 필요성, 비용, 데이터 전송 범위를 설명한다.

## 6. 성공 조건

- LLM 입력이 확정된 운영 결과로 제한된다.
- 보고서의 모든 수치가 입력 결과와 일치한다.
- AI가 품질 상태를 변경하거나 새로 판정하지 않는다.
- 실패 검사와 점검 우선순위가 읽기 쉽게 정리된다.
- 생성 결과에 기준 `run_id`가 포함된다.
- LLM 실패 시 규칙 기반 보고서가 생성된다.
- 원본 검사 결과는 AI 성공 여부와 관계없이 조회 가능하다.
- 보고서 자동 전송 전에 사람 검토 단계가 있다.
- 토큰과 비밀값이 로그 또는 저장소에 남지 않는다.

## 7. 실패 가능성

- LLM API 인증, 네트워크, 할당량 문제가 발생할 수 있다.
- 모델이 입력에 없는 원인을 추정할 수 있다.
- 숫자나 상태를 잘못 옮길 수 있다.
- 긴 오류 목록으로 입력 한도를 초과할 수 있다.
- 민감하거나 식별 가능한 상세가 입력에 포함될 수 있다.
- 같은 실행에 중복 보고서가 생성될 수 있다.
- AI 문구가 실제 조치 완료를 암시할 수 있다.
- 비용과 응답 시간이 예상보다 커질 수 있다.

## 8. 확인 및 복구

- 생성 전 입력 스키마와 허용 필드를 검증한다.
- 생성 후 핵심 수치와 상태가 입력에 존재하는지 기계적으로 대조한다.
- 검증 실패 출력은 배포하지 않고 대체 보고서를 사용한다.
- 동일 `run_id`와 보고서 버전에 멱등 키를 적용한다.
- API 실패 시 재시도 횟수를 제한하고 실패 원인을 기록한다.
- 원본 품질 결과와 운영 지표 링크를 보고서에 포함한다.
- 사람 검토 전 Slack 또는 Jira에 자동 전송하지 않는다.
- 프롬프트와 템플릿 변경은 버전으로 관리한다.

## 9. 채용공고 요구사항과의 연결

- AI 도구를 이용한 반복 운영 업무 자동화
- 정기 리포트와 장애 요약 작성
- 품질 검사와 지표 이상 모니터링 결과의 전달
- AI의 역할과 결정 권한을 제한하는 안전한 설계
- 실패 시 대체 경로를 제공하는 운영 안정성
- 구조화된 데이터와 자연어 보고서의 연결

## 10. 미확정 사항

- 사용할 LLM 제공자와 모델
- 인증과 비밀값 저장 방식
- 호출 비용 및 토큰 한도
- 보고서 생성 주기
- 이상 항목 우선순위 규칙
- 프롬프트와 출력 스키마
- 사람 검토 절차와 승인 상태
- Slack 및 Jira 실제 연동 범위
- 보고서 보존 기간
- 재시도와 타임아웃 정책
- 입력 데이터 비식별 검증 방식
