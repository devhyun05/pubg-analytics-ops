# BI 대시보드

> 문서 상태: 초기 설계
>
> 구현 상태: 미구현
>
> BI 역할: 확정된 분석 및 운영 결과의 탐색과 모니터링

## 1. 목적

이 단계는 PostgreSQL에 저장된 지표와 품질 결과를 Superset으로 시각화해 분석가와 운영 담당자가 현재 상태를 빠르게 이해하고 조치할 수 있게 한다.

BI는 데이터의 정상 여부를 직접 계산하지 않는다. Python과 SQL이 계산한 품질 상태, 오류 건수, 지표를 사람이 확인하기 쉬운 형태로 제공한다.

## 2. 입력

이 단계는 [06_RESULT_STORAGE.md](06_RESULT_STORAGE.md)의 출력을 입력으로 받는다.

- PostgreSQL의 게임 분석 지표
- 데이터 운영 지표
- 파이프라인 실행 이력
- 품질 검사 결과
- 스키마 변경 이력
- 조회용 뷰
- 지표 및 데이터 갱신 시각

대시보드는 원본 CSV나 전체 상세 이벤트를 직접 조회하지 않는다.

## 3. 처리

### Gameplay Metrics Dashboard

목표는 사용 가능한 게임 데이터의 주요 패턴을 탐색하는 것이다.

후보 구성은 다음과 같다.

| 구성 | 목적 | 상태 |
|---|---|---|
| 전체 경기 및 이벤트 규모 | 현재 분석 대상 범위 확인 | 지표 확정 필요 |
| 맵별 경기 수 | 데이터의 맵 구성 비교 | 컬럼 확인 필요 |
| 게임 모드별 경기 수 | 플레이 방식 구성 비교 | 컬럼 확인 필요 |
| 무기 또는 원인별 처치 비율 | 사망 이벤트 구성 탐색 | 컬럼 확인 필요 |
| 경기당 평균 이벤트 수 | 경기 단위 이벤트 밀도 확인 | 조인 키 확인 필요 |
| 평균 교전 거리 | 위치 기반 패턴 탐색 | 좌표 단위 확인 필요 |

후보 필터는 맵, 게임 모드, 데이터 기간, 배치 또는 데이터 버전이다. 실제 제공 필터는 데이터 사전과 지표 스키마를 확인한 뒤 확정한다.

대시보드에는 공개된 전체 데이터 규모와 실제 처리한 데이터 규모를 구분해 표시한다.

### Data Operations Dashboard

목표는 파이프라인의 정상 실행과 데이터 최신성을 확인하는 것이다.

후보 구성은 다음과 같다.

| 구성 | 운영 질문 |
|---|---|
| 최근 실행 상태 | 마지막 파이프라인은 성공했는가 |
| 마지막 정상 갱신 시각 | 데이터가 언제 마지막으로 정상 게시됐는가 |
| 입력·출력·실패 행 수 | 처리 중 데이터 손실 또는 실패가 있었는가 |
| 품질 검사 성공률 | 전체 검사 중 정상 통과 비율은 얼마인가 |
| 실패 및 경고 검사 | 어떤 규칙에서 문제가 발생했는가 |
| 오류 건수와 오류율 | 문제의 크기는 어느 정도인가 |
| 배치 데이터량 변화 | 이전 정상 배치 대비 급감·급증했는가 |
| 처리 시간 추이 | 파이프라인 성능이 악화되고 있는가 |
| 스키마 변경 | 새 컬럼, 누락 컬럼, 타입 변화가 있었는가 |

상태 색상과 임계값은 품질 및 운영 규칙의 결과를 그대로 사용한다. Superset 차트에서 별도의 비즈니스 판정 로직을 중복 구현하지 않는다.

### 접근과 갱신

- Superset은 PostgreSQL 조회용 계정을 사용한다.
- 대시보드 데이터셋은 적재 테이블보다 안정된 조회용 뷰를 우선 사용한다.
- 최신 갱신 시각과 대상 `run_id`를 대시보드에 표시한다.
- 필터가 지표의 집계 단위와 맞지 않으면 제공하지 않는다.
- 실패 배치는 Gameplay 대시보드의 최신 정상 결과를 덮어쓰지 않는다.

## 4. 출력

이 단계의 출력은 두 개의 Superset 대시보드다.

1. `Gameplay Metrics Dashboard`
2. `Data Operations Dashboard`

대시보드에는 다음 메타정보를 표시한다.

- 데이터셋 버전
- 실제 처리 범위
- 최신 정상 `run_id`
- 마지막 정상 갱신 시각
- 적용된 지표 버전
- 품질 상태

Data Operations Dashboard에서 확인한 품질 및 이상 결과는 [08_AI_REPORT_AUTOMATION.md](08_AI_REPORT_AUTOMATION.md)가 사용하는 구조화된 PostgreSQL 결과와 동일한 근거를 사용한다.

## 5. 사용 기술

- Apache Superset
- PostgreSQL
- SQL 조회용 뷰
- Docker Compose

Superset 내부 계산은 표시 목적의 간단한 포맷에 제한하고, 핵심 지표 계산은 버전 관리 가능한 SQL 단계에서 수행한다.

## 6. 성공 조건

- Gameplay와 Data Operations 대시보드가 분리된다.
- 대시보드가 원본 CSV를 직접 조회하지 않는다.
- 최신 정상 갱신 시각과 실제 처리 범위가 표시된다.
- 품질 실패와 경고를 규칙별로 탐색할 수 있다.
- 이전 배치 대비 데이터량과 처리 시간 변화를 볼 수 있다.
- 필터가 지표 정의와 일치한다.
- BI에서 품질 또는 정상 여부를 중복 계산하지 않는다.
- 데스크톱 화면에서 주요 상태를 빠르게 파악할 수 있다.

## 7. 실패 가능성

- PostgreSQL 연결 또는 권한 설정이 실패할 수 있다.
- 대시보드가 오래된 캐시를 보여줄 수 있다.
- 잘못된 조인이나 필터로 지표가 중복될 수 있다.
- 최신 실패 배치가 최신 정상 결과로 보일 수 있다.
- 차트가 실제 처리 범위를 전체 데이터로 오해하게 만들 수 있다.
- 너무 많은 차트로 핵심 운영 상태가 묻힐 수 있다.
- Superset 내 계산과 SQL 지표 정의가 달라질 수 있다.

## 8. 확인 및 복구

- 차트 값과 원본 PostgreSQL 조회 결과를 대조한다.
- 모든 차트에 데이터 갱신 기준을 연결한다.
- 캐시 갱신 실패 여부와 마지막 조회 시각을 확인한다.
- 실패 배치와 정상 게시 배치를 구분하는 뷰를 사용한다.
- 권한 문제는 읽기 전용 계정과 대상 스키마 권한을 확인한다.
- 대시보드 내보내기 파일로 구성을 재현할 수 있게 한다.
- 지표 정의가 바뀌면 SQL 버전과 대시보드 설명을 함께 갱신한다.

## 9. 채용공고 요구사항과의 연결

- Apache Superset을 활용한 BI 경험
- 분석 지표와 운영 지표의 목적별 대시보드 설계
- 품질 결과와 데이터 최신성 모니터링
- 사용자가 빠르게 이상을 확인할 수 있는 정보 구조
- SQL 결과를 신뢰 가능한 시각화로 전달하는 능력
- 실제 처리 범위와 전체 규모를 구분하는 정확한 커뮤니케이션

## 10. 미확정 사항

- 최종 게임 분석 지표
- 차트 종류와 레이아웃
- 확정 필터
- 상태별 색상과 표시 규칙
- PostgreSQL 조회용 뷰
- Superset 사용자와 권한
- 캐시와 자동 새로고침 주기
- 대시보드 내보내기 및 버전 관리 방식
- 모바일 화면 지원 범위
- 스크린샷 또는 공개 데모 방식
