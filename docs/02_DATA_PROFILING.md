# 02. 데이터 프로파일링

## 1. 현재 상태

상태: **현재 환경 사망 분석 범위의 프로파일링 완료**

현재 단계에서는 데이터를 삭제하거나 정제하지 않았다. 원본 deaths CSV 5개를
DuckDB로 읽어 분석에 필요한 컬럼의 실제 상태를 측정했다.

다음 작업은 확정한 품질 플래그와 제외 사유를 적용하는 분석용 DuckDB 뷰를
구현하는 것이다.

## 2. 프로파일링 목적

현재 분석 질문은 다음과 같다.

> 에란겔과 미라마에서 `Falling`과 `Drown` 사망이 특정 위치에 여러 경기와
> 날짜에 걸쳐 반복적으로 집중되는가?

프로파일링의 목적은 이 질문에 필요한 컬럼이 실제로 존재하고 공간·날짜 분석에
사용할 수 있는 상태인지 판단할 근거를 만드는 것이다.

## 3. 입력 범위

### deaths 파일

| 파일 | 행 수 |
|---|---:|
| `kill_match_stats_final_0.csv` | 13,426,348 |
| `kill_match_stats_final_1.csv` | 13,440,889 |
| `kill_match_stats_final_2.csv` | 13,431,052 |
| `kill_match_stats_final_3.csv` | 13,431,331 |
| `kill_match_stats_final_4.csv` | 11,640,855 |
| 합계 | 65,370,475 |

고유 `match_id`는 722,425개다.

### 분석 대상 컬럼

| 컬럼 | 출처 | 역할 |
|---|---|---|
| `killed_by` | deaths | `Falling`과 `Drown` 사망 분류 |
| `map` | deaths | 에란겔과 미라마 분리 |
| `match_id` | deaths | 경기 반복 수 계산과 날짜 연결 |
| `victim_position_x` | deaths | 피해자 X 좌표 |
| `victim_position_y` | deaths | 피해자 Y 좌표 |
| `date` | aggregate | 여러 날짜에 반복됐는지 확인 |

deaths 원본에는 `date`가 없다. aggregate에서 경기당 하나의 날짜를 만든 뒤
`match_id`로 연결한다.

## 4. 실행 방법

기본 프로파일러:

```text
scripts/profile_deaths.py
```

중복 프로파일러:

```text
scripts/profile_death_duplicates.py
```

스키마 및 최종 분석 적격성 프로파일러:

```text
scripts/profile_input_schemas.py
scripts/profile_analysis_eligibility.py
```

실행 명령:

```bash
python scripts/profile_deaths.py
python scripts/profile_death_duplicates.py
python scripts/profile_input_schemas.py
python scripts/profile_analysis_eligibility.py
```

처리 방식:

- pandas로 전체 CSV를 메모리에 적재하지 않음
- DuckDB `read_csv_auto`로 CSV 5개 조회
- 핵심 문자열을 공백 제거 후 측정
- 좌표를 `TRY_CAST`로 숫자 변환
- 파일별·맵별·사망 원인별 SQL 집계
- 원본 파일을 변경하지 않음

전체 프로파일러 실행 시간은 40.2859초였다.
중복 전체 프로파일링 실행 시간은 218.4066초였다.
전체 타입 추론과 최종 적격성 측정의 통합 실행 시간은 395.7318초였다.

## 6. 맵 분포

| 맵 | 행 수 | 고유 경기 |
|---|---:|---:|
| `ERANGEL` | 52,964,245 | 579,541 |
| `MIRAMAR` | 11,622,838 | 133,991 |
| NULL | 783,392 | 8,893 |

맵 NULL 행은 전체 사망 원인 집계에는 사용할 수 있지만 에란겔·미라마 공간 분석에는
사용할 수 없다.

### 경기 단위 map 결측 조사

`map`이 NULL인 783,392행은 해당 행의 맵 이름이 기록되지 않았다는 뜻이다.
전체 deaths의 1.198388%이며 8,893개 `match_id`에 속한다.

같은 `match_id`의 다른 행에서 맵을 복구할 수 있는지 확인한 결과:

| 항목 | 행 수 또는 경기 수 |
|---|---:|
| `map` NULL 행 | 783,392 |
| `map` NULL이 있는 경기 | 8,893 |
| 같은 경기의 고유 맵으로 복구 가능한 행 | 0 |
| 경기의 모든 행에서 `map`이 NULL인 행 | 783,392 |
| 경기의 모든 행에서 `map`이 NULL인 경기 | 8,893 |
| 한 경기에서 여러 맵이 충돌한 경기 | 0 |

즉, 일부 행만 우연히 비어 있는 것이 아니라 해당 8,893개 경기 전체에서 맵이
누락됐다. 좌표·파일명·날짜로 에란겔 또는 미라마를 추정하지 않는다.

환경 사망 영향:

| 원인 | `map` NULL 행 | 같은 경기에서 복구 가능 | 복구 불가능 |
|---|---:|---:|---:|
| `Drown` | 3,483 | 0 | 3,483 |
| `Falling` | 6,970 | 0 | 6,970 |
| 합계 | 10,453 | 0 | 10,453 |

5개 원본 파일의 `map` 결측률은 약 1.16~1.24%로 비슷했다. 특정 파일 하나의
손상으로 한정되는 패턴은 아니다.

현재 처리 규칙:

- 원본 행과 NULL을 그대로 보존한다.
- 맵이 필요 없는 전체 사망 원인 집계에는 포함할 수 있다.
- 맵별 환경 사망, 좌표 격자와 핫스팟 분석에서는 제외한다.
- 제외 사유는 `MISSING_MAP`으로 기록한다.

### 좌표 범위 검사 기준

[PUBG 공식 Telemetry Objects 문서](https://documentation.pubg.com/en/telemetry-objects.html)는
위치 단위를 센티미터로 설명하며 에란겔과 미라마의 X·Y 축 범위를 각각
`0~816,000`으로 제시한다. 이 범위를 현재 데이터셋의 공간 유효성 검사 기준으로
사용했다.

이 기준은 범위 밖 행을 찾기 위한 프로젝트 기준이다. Kaggle CSV의 생성 과정이
완전히 공개되어 있지 않으므로 범위 밖 값을 실제 게임 오류라고 확정하지 않고
분석 제외 및 원본 보존 후보로 관리한다.

### 실제 예시

플레이어 이름은 포함하지 않았으며 `match_id`는 문서에서 축약했다. 프로파일러를
실행하면 로컬에서 전체 `match_id`와 원본 파일을 확인할 수 있다.

| 원인 | 맵 | X | Y | 위반 |
|---|---|---:|---:|---|
| `Falling` | 에란겔 | 930,233.3 | 364,903.9 | X > 816,000 |
| `Drown` | 에란겔 | 241,438.8 | -101,266.9 | Y < 0 |

`0,0`은 공식 숫자 범위 안의 원점이므로 위 71행에는 포함되지 않는다. 다만 현재
CSV에서는 실제 사망 위치로 해석하기 어려운 `0,0` 사례가 많아 공간 분석에서는
별도의 위치 미제공 또는 비정상 후보로 관리한다.

### 범위 밖 값의 현재 해석

71행은 공식 좌표 범위를 벗어났다는 점에서는 이상값이 맞지만, 그 원인을 단순한
CSV 오류나 실제 게임 오류 중 하나로 확정할 수는 없다.

현재 관측된 특징:

- 전체 65,370,475행 중 71행뿐이어서 시스템 전체의 좌표 변환이 잘못된 현상은
  아니다.
- 환경 사망은 전체 deaths의 약 1.5%지만 범위 밖 71행 중 25행, 약 35.2%를
  차지한다.
- 범위 밖 환경 사망 중 `Falling`이 21행, `Drown`이 4행이다.
- 모든 좌표가 숫자로 정상 파싱됐으므로 단순한 문자열 숫자 변환 실패는 아니다.

가능한 원인 후보:

- 원본 텔레메트리 기록 또는 Kaggle CSV 변환 과정의 좌표 이상
- 경기 시작 전후 또는 일반 플레이 영역 밖에서 기록된 위치
- 낙하·물리 처리 중 캐릭터가 정상 맵 경계 밖에 있었던 게임 상태
- 당시 맵 버전과 현재 공식 좌표 문서 사이의 차이
- 실제 게임 또는 맵의 드문 오류

현재 데이터만으로는 어느 원인인지 구분할 수 없다. 따라서 값을 `0`이나
`816,000`으로 강제 보정하지 않고 `OUT_OF_MAP_BOUNDS` 후보로 보존하며, 공간
핫스팟 입력에서는 제외하는 방향을 사용한다. 원인 확인을 위해서는 해당 행의
`time`, 동일 `match_id`의 다른 위치, 좌표값 반복 여부를 추가로 비교해야 한다.

### Drown `0,0` 집중 조사

`Drown`의 60.403663%가 `0,0`이라는 결과는 271,712개의 익사 행 중
164,124행의 피해자 X·Y가 모두 정확히 숫자 0이라는 뜻이다. 이것만으로
164,124명이 실제 맵 왼쪽 위에서 익사했다고 해석할 수는 없다.

#### 전체와 경기 커버리지

| 항목 | 결과 |
|---|---:|
| 전체 `Drown` 행 | 271,712 |
| `0,0` 행 | 164,124 |
| `0,0` 비율 | 60.403663% |
| `Drown` 발생 경기 | 164,546 |
| `0,0 Drown` 발생 경기 | 92,002 |
| `Drown` 경기 중 `0,0` 발생 경기 비율 | 55.912632% |
| X만 0 또는 Y만 0인 행 | 0 |

`0,0 Drown`은 한두 경기의 오류가 아니라 92,002개 경기에 분산되어 있다.
경기당 중앙값은 1행, 95백분위는 4행, 최댓값은 25행이었다.

#### 맵별 결과

| 맵 | 전체 `Drown` | `0,0` | 비율 |
|---|---:|---:|---:|
| 에란겔 | 231,034 | 133,757 | 57.894942% |
| 미라마 | 37,195 | 28,214 | 75.854281% |
| 맵 NULL | 3,483 | 2,153 | 61.814528% |

CSV 5개에서도 각각 59.989212%에서 60.861992% 사이로 비슷하게 반복됐다.
특정 맵이나 특정 파일 하나가 손상돼 생긴 현상으로 보기는 어렵다.

#### 원점 주변 분포

| 위치 조건 | 행 수 |
|---|---:|
| 정확히 `0,0` | 164,124 |
| `0,0` 제외 원점 10m 사각형 안 | 0 |
| `0,0` 제외 원점 100m 사각형 안 | 2 |
| 두 번째로 많이 반복된 정확한 좌표 | 4 |

정확한 `0,0`에만 164,124행이 쌓이고 바로 주변에는 사실상 데이터가 없다.
연속적인 실제 위치 분포보다는 위치 미제공 또는 특수 상태를 나타내는
sentinel value 패턴에 가깝다.

#### `time` 분포 비교

`time` 값의 시작 기준은 현재 원본 설명을 추가 확인해야 하므로 절대적인 게임
단계로 단정하지 않고 두 그룹의 상대 분포만 비교했다.

| 위치 그룹 | 25백분위 | 중앙값 | 75백분위 | 평균 |
|---|---:|---:|---:|---:|
| `0,0` | 168 | 170 | 176 | 229.56 |
| 비영점 | 286 | 674 | 1,040 | 704.53 |

`0,0` 그룹은 164,124행 중 144,322행, 약 87.9%가 `time` 120 이상
300 미만에 집중됐다. 비영점 그룹과 분포가 크게 달라 위치 누락이 특정 게임
상태 또는 데이터 생성 규칙과 연관됐을 가능성이 있다.

#### 관련 필드

- `0,0` 그룹 164,124행 중 162,830행은 killer 이름과 좌표가 모두 없었다.
- 피해자 등수는 `0,0` 그룹에서 3행만 NULL이었다.
- 따라서 행 전체가 비어 있는 것은 아니며, 사망 사건은 기록됐지만 위치 또는
  환경 사망 관련 세부 정보가 제한된 패턴으로 해석하는 것이 안전하다.

#### 현재 결론

현재 환경 사망 공간 분석에서는 정확한 `0,0`을 실제 맵 원점으로 사용하지 않고
`INVALID_OR_UNAVAILABLE_POSITION`으로 분류한다. 원본과 전체 사망 원인
건수에는 보존하지만 히트맵, 격자별 사망 수, 핫스팟 지표에서는 제외한다.

이 규칙을 적용하면 맵과 유효 범위 좌표가 있는 `Drown` 공간 분석 후보는
106,254행이다. 날짜 연결과 중복 검사를 적용하기 전의 수치이므로 최종 분석
행 수는 아니다.

## 10. 확인된 사실과 미확정 해석

### 확인된 사실

- `killed_by`, `match_id`, 피해자 X·Y 좌표에는 NULL이나 빈 문자열이 없다.
- `map`은 783,392행에서 없다.
- `map`이 없는 8,893개 경기에서는 모든 사망 행의 `map`이 NULL이다.
- 같은 `match_id`에서 에란겔과 미라마가 충돌한 경기는 0건이다.
- 피해자 좌표가 정확히 `0,0`인 행은 2,958,383건이다.
- 공식 좌표 범위 밖 행은 71건으로 전체의 0.000108612%다.
- 환경 사망 중 공식 좌표 범위 밖 행은 25건이다.
- `Drown`의 60.40%가 `0,0` 좌표다.
- 주먹 사망 샘플에서 killer 위치와 victim의 `0,0`을 실제 위치로 함께 해석할 수
  없는 사례가 확인됐다.

### 합리적인 추정

- 현재 데이터의 `0,0` 중 상당수는 실제 사망 위치를 나타내지 않을 가능성이 있다.

### 아직 확정하지 않은 내용

- `0,0`이 저장된 원인이 접속 종료, 잠수 또는 수집 오류인지
- 범위 밖 값이 만들어진 정확한 원인
- 상세값이 다른 이벤트 후보가 같은 사건인지 별개의 사건인지

`0,0`을 게임 시작 직후 종료나 잠수 플레이로 분류하지 않는다.

## 11. 현재 분석 범위 결정

현재 프로젝트가 정의한 지형 기반 환경 사망:

```text
Falling
Drown
```

이 두 값이 데이터의 모든 비전투 사망을 의미하지는 않는다. 전체 58개
`killed_by` 값을 다시 확인한 결과 다음과 같은 다른 후보도 존재했다.

| 원인 | 행 수 | 현재 메인 분석에서 제외하는 이유 |
|---|---:|---|
| `Bluezone` | 3,203,327 | 동적으로 이동하는 자기장과 시간·플레이 행동 영향 |
| `RedZone` | 82,888 | 무작위 또는 동적 위험 구역 영향 |
| `death.RedZoneBomb_C` | 779 | `RedZone`과의 의미·버전 관계 추가 확인 필요 |
| `Hit by Car` | 609,849 | 플레이어 운전 행동과 차량 노출 영향 |
| 차량 이름별 원인 | 다수 | 고정 지형보다 플레이어·차량 상호작용 영향 |
| 화염·Molotov 원인 | 다수 | 전투 행동으로 발생한 피해일 가능성 |

현재 질문은 고정된 맵 위치에서 반복되는 지형·물 관련 사망을 찾아 맵 QA 점검
후보를 만드는 것이다. 따라서 `Falling`과 `Drown`만 메인 범위에 남기고
Bluezone·RedZone·차량 원인은 서로 다른 분석 질문의 후속 후보로 관리한다.

현재 해석 방향:

- `Falling`은 비영점 위치 커버리지가 약 97%여서 메인 공간 분석 후보로 적합하다.
- `Drown`은 비영점 위치 커버리지가 약 39.11%이므로 보조 분석으로 사용하고
  대표성 한계를 표시해야 한다.
- `0,0`은 전체 사망 건수에는 포함할 수 있지만 공간 히트맵에서는 제외 후보로
  관리한다.
- 공식 범위 밖 71행은 원본에 보존하되 공간 핫스팟 분석에서 제외한다.
- 환경 사망의 정확한 `0,0`은 원본에 보존하되 공간 핫스팟 분석에서 제외한다.
- 현재 환경 사망 분류가 PUBG의 공식 전체 환경 사망 분류라고 주장하지 않는다.
- 메인 분석 명칭은 의미를 분명히 하기 위해 `지형 기반 환경 사망`으로 설명한다.

경기 상세와 텔레메트리 JSON을 조회했다. 이 파일럿은 최신 데이터의 실제 구조와
대략적인 전송량을 확인하기 위한 것이며 모집단 분석 결과가 아니다.

실행 결과는 다음과 같다.

| 항목 | 결과 |
|---|---:|
| 요청 경기 | 10 |
| 성공 경기 | 10 |
| 실패 경기 | 0 |
| 전체 텔레메트리 이벤트 | 228,142 |
| 사망 이벤트 | 399 |
| 피해자 좌표가 있는 사망 이벤트 | 399 |
| 피해자 좌표가 정확히 `0,0`인 사망 이벤트 | 0 |
| 실제 전송 크기 | 7.16 MB |
| 압축 해제 후 JSON 크기 | 135.87 MB |
| 실행 시간 | 13.06초 |
| 경기 시각 범위 | 2026-07-30 23:19:13~2026-07-31 00:54:41 UTC |

맵 구성은 다음과 같았다.

| API `mapName` | 경기 수 | 해석 |
|---|---:|---|
| `Range_Main` | 6 | 훈련장 계열, 현재 분석 대상 아님 |
| `Desert_Main` | 2 | Miramar |
| `Baltic_Main` | 1 | Erangel |
| `Tiger_Main` | 1 | Taego |

10개 중 6개가 분석 대상이 아닌 `Range_Main`이었다. 따라서 968개 텔레메트리를
바로 모두 저장하지 않고, 경기 상세의 `mapName`을 먼저 조회해 `Baltic_Main`과
`Desert_Main`만 선별한 뒤 텔레메트리를 수집한다.

최신 사망 이벤트는 `LogPlayerKillV2`였으며 다음 피해정보 객체가 확인됐다.

```text
killerDamageInfo
finishDamageInfo
dBNODamageInfo
```

각 객체에는 다음 필드가 있었다.

```text
damageTypeCategory
damageCauserName
damageReason
distance
additionalInfo
isThroughPenetrableWall
```

세 피해정보 객체 전체에서 `Damage_Drown` 3회와 `Damage_Instant_Fall` 1회가
확인됐다. 이는 환경 사망 분류에 사용할 공식 후보 값이 최신 데이터에도 존재함을
보여준다. 다만 이 숫자는 세 객체의 **필드 출현 횟수**를 합친 값으로, 고유 사망
이벤트 수나 최종 환경 사망 건수가 아니다. DBNO 원인, 마무리 피해와 직접 사망 중
어떤 객체를 최종 원인으로 선택할지 규칙을 먼저 정의해야 한다.

재현 명령은 다음과 같다. 경기 상세와 텔레메트리 조회에는 API 키를 전달하지
않는다.

```bash
python scripts/profile_pubg_api_pilot.py --platform steam --limit 10
```

집계 결과에는 플레이어 이름과 계정 ID를 저장하지 않는다. 결과 JSON은 Git에서
제외되는 `data/raw/pubg_api/pilot/steam/profile_summary.json`에 기록한다.
