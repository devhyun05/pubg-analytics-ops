# Data Analytics 역할과 협업 경계

> 문서 상태: 공개 자료 조사 완료
>
> 확인일: 2026-07-31
>
> 적용 범위: 환경 사망 핫스팟 분석과 맵 QA 점검 후보 전달 시나리오

## 1. 결론

Data Analytics의 역할은 완성된 요구 문서를 받아 숫자로 바꾸고 QA에 전달하는
일방향 작업으로 한정되지 않는다.

분석가는 보통 이해관계자와 함께 모호한 문제를 측정 가능한 질문으로 바꾸고,
데이터 정의와 품질을 확인하며, 지표·분석·대시보드를 만들고, 결과의 의미와
한계를 설명한다. 발견한 패턴은 실행 가능한 점검 후보와 우선순위로 전달하고,
변경이 이루어진 뒤 같은 지표로 효과와 부작용을 다시 확인한다.

QA는 실제 빌드에서 테스트 전략과 테스트 케이스를 만들고 현상을 재현하며,
제품 문제의 원인을 확인하는 역할에 더 가깝다. 게임 디자인, 레벨 디자인,
제품 또는 라이브 운영 조직은 분석과 QA 결과를 함께 검토해 실제 변경 여부와
수정 방향을 결정하고, 개발 조직이 이를 구현한다.

### 요구 문서와 측정 정의의 소유권

실무에서 분석가는 항상 완성된 측정 명세를 받는 것도 아니고 모든 문제를 혼자
정의하는 것도 아니다. 요청자는 해결하려는 문제와 의사결정 목적을 설명하고,
분석가는 이를 계산 가능한 지표로 설계한 뒤 요청자와 의미를 합의한다.

기존 정기 KPI나 공식 지표는 지표 사전과 기존 정의를 따른다. 분석가가 임의로
분모나 필터를 바꾸지 않으며, 변경이 필요하면 지표 버전과 변경 이유를 남긴다.

신규 분석 요청은 다음과 같은 형태로 들어올 수 있다.

| 요청 출처 | 요청 예시 |
|---|---|
| 게임 디자인·제품 | 신규 맵 변경이 플레이 흐름에 어떤 영향을 주었는가 |
| 라이브 운영 | 패치 이후 특정 지표가 비정상적으로 변했는가 |
| QA | 특정 위치의 제보가 전체 데이터에서도 반복되는가 |
| CS·커뮤니티 | 반복되는 사용자 불편이 실제 게임 데이터에서도 관찰되는가 |
| 분석가의 모니터링 | 대시보드나 이상 탐지에서 예상하지 못한 변화가 발견됨 |

신규 질문에서는 분석가가 다음 측정 항목을 제안한다.

| 항목 | 정의할 내용 |
|---|---|
| 의사결정 | 결과를 보고 누가 무엇을 결정할 것인가 |
| 분석 대상 | 어떤 유저, 경기, 맵과 이벤트를 포함할 것인가 |
| 기간 | 시작·종료 시각과 비교 기간 |
| 분석 단위 | 유저, 경기, 날짜, 위치 격자 등 |
| 분자·분모 | 무엇을 세고 무엇으로 나눌 것인가 |
| 차원 | 맵, 모드, 지역, 원인 등 어떤 기준으로 나눌 것인가 |
| 제외 규칙 | NULL, 중복, 테스트 경기와 비정상 값을 어떻게 처리할 것인가 |
| 품질 조건 | 결과를 게시하기 전에 통과해야 할 검사 |
| 판단 기준 | 어떤 결과를 모니터링 또는 QA 점검 후보로 볼 것인가 |
| 출력 형태 | SQL 결과, 대시보드, 알림 또는 분석 보고서 |

분석가는 위 정의를 조용히 혼자 확정하지 않는다. 요청자는 비즈니스·게임 의미와
의사결정 목적을 확인하고, 분석가는 데이터로 계산 가능하며 오해 없이 재현되는
정의인지 확인한다. 필요한 이벤트가 없다면 추측해서 계산하지 않고 데이터
엔지니어링 또는 게임 개발 조직에 로깅 요구사항을 전달한다.

## 3. 공개 자료로 확인할 수 없는 내용

다음 내용은 KRAFTON 또는 PUBG Studios의 공개 자료에서 확인되지 않았다.

- Data Analytics Operation 인턴의 현재 내부 표준 업무 절차
- 분석 요청서의 정확한 양식과 승인 과정
- 분석 결과를 QA에 전달하는 티켓 시스템과 필수 필드
- 환경 사망 핫스팟을 처리하는 실제 담당 조직
- 분석가, QA, 레벨 디자이너와 개발자의 내부 RACI
- 패치 검토를 시작하는 내부 임계값
- 분석가가 맵 수정 여부에 갖는 최종 의사결정 권한

따라서 포트폴리오에서 이 문서의 협업 흐름을 KRAFTON의 실제 내부 프로세스라고
표현하지 않는다. 공개 채용 공고와 공식 PUBG 변경 사례를 바탕으로 설계한
합리적인 포트폴리오 운영 시나리오라고 명시한다.

## 4. 공개 자료를 바탕으로 추론한 협업 흐름

다음 흐름은 공개 자료를 종합한 추론이며 KRAFTON 내부 절차로 확인된 것은 아니다.

```text
게임 디자인·라이브 운영·QA의 질문 또는 분석가의 이상 탐지
→ 분석가와 이해관계자가 문제와 성공 기준 합의
→ 필요한 이벤트·컬럼·데이터 품질 확인
→ SQL 지표, 대시보드와 이상 후보 생성
→ 분석가가 규모·반복성·한계와 우선순위를 설명
→ QA가 실제 빌드에서 재현하고 원인·심각도 확인
→ 게임 디자인·제품·라이브 운영이 변경 여부 결정
→ 레벨 디자인·개발 조직이 구현하고 QA가 검증
→ 출시 후 분석가가 같은 지표와 플레이어 피드백을 모니터링
→ 유지, 추가 조정 또는 롤백 판단
```

이 과정은 일방향 전달보다 반복 협업에 가깝다. QA 결과에서 정상 플레이로
확인되면 분석 정의를 수정할 수 있고, 분석 과정에서 필요한 이벤트가 부족하면
데이터 엔지니어 또는 게임 개발 조직에 로깅 개선을 요청할 수 있다.

| 맵·게임 규칙 변경 결정 | 게임 디자인·제품·라이브 운영 | 효과 예상과 데이터 근거를 제안하되 최종 결정하지 않음 |

| 출시 전 회귀 테스트 | QA | 필요 지표 또는 테스트 데이터 지원 |
| 출시 후 효과 측정 | Data Analytics | 직접 책임 |

## 6. 이 프로젝트에서 분석가가 제공할 산출물

환경 사망 분석의 최종 전달 대상은 단순 CSV가 아니라 다음 내용을 포함한
QA 점검 후보 패키지다.

| 항목 | 내용 |
|---|---|
| `candidate_id` | 점검 후보의 고유 식별자 |
| 맵과 위치 | 맵, 격자 범위, 중심 X·Y 좌표 |
| 사망 유형 | `Falling` 또는 `Drown` |
| 규모 | 사망 수와 위치 내 환경 사망 비율 |
| 반복성 | 고유 경기 수와 고유 날짜 수 |
| 안정성 | 여러 격자 크기에서 순위가 유지되는지 |
| 데이터 품질 | 적용 규칙, 제외 건수와 품질 상태 |
| 시각 자료 | 과거 지도 확대 이미지와 위치 표시 |
| 해석 | 가능한 설명과 현재 데이터로 확인할 수 없는 내용 |
| 우선순위 | `MONITOR`, `QA_REVIEW` 등 제안 상태 |
| 요청 사항 | QA에서 확인할 빌드, 지형, 충돌, 수면과 이동 경로 |

분석가는 다음 문장까지 책임질 수 있다.

> 이 위치에서 환경 사망이 여러 경기와 날짜에 걸쳐 반복됐고, 데이터 품질
> 문제와 한 경기의 극단값만으로 설명되지 않아 QA 점검 우선순위가 높다.

분석가가 현재 데이터만으로 말하면 안 되는 문장은 다음과 같다.

> 이 위치의 오브젝트에 버그가 있으며 특정 방식으로 수정해야 한다.

## 7. 이 프로젝트에서 수행하지 못하는 부분

현재 데이터는 2017~2018년 정적 공개 데이터이므로 다음 단계는 실제로 완료할
수 없다.

- 당시 게임 빌드에서 현상 재현
- 충돌·물리·수면 깊이와 정확한 오브젝트 원인 확인
- 내부 QA 티켓 생성과 담당자 배정
- 실제 맵 수정
- 신규 배치로 패치 전후 효과 검증

포트폴리오에서는 위 단계를 완료했다고 표현하지 않고, QA가 사용할 수 있는
점검 후보와 후속 측정 설계까지 구현한다.

## 8. 면접 답변 예시

> 데이터 분석가는 완성된 문서를 받아 수치만 만드는 역할이 아니라, 이해관계자의
> 질문을 측정 가능한 지표로 바꾸고 데이터 품질을 확인하며 분석 결과를 의사결정
> 가능한 형태로 전달하는 역할이라고 이해했습니다. 제 프로젝트에서는 환경 사망
> 집중 위치를 여러 경기와 날짜 기준으로 선별하고 QA 점검 후보 패키지를 만드는
> 데까지 분석가의 책임으로 정의했습니다. 실제 버그 재현과 원인 판정은 QA와
> 개발 조직의 영역이고, 수정 여부는 게임 디자인과 제품 조직이 결정합니다.
> 변경 후에는 분석가가 동일 지표로 효과와 부작용을 다시 모니터링하는 구조를
> 설계했습니다.

## 9. 자체 정의 분석 브리프와 STAR의 관계

사이드 프로젝트에서는 실제 회사 요청서를 추측해 만드는 대신 `자체 정의 분석
브리프`를 작성한다. 이 브리프는 분석을 시작한 배경, 답할 질문과 결과의 가상
활용 대상을 정의한다. STAR는 브리프의 질문을 해결하기 위해 지원자가 실제로
수행한 판단, 구현과 측정 결과를 설명한다.

| 분석 브리프 항목 | STAR 연결 |
|---|---|
| 왜 이 분석이 필요한가 | `Situation` |
| 무엇을 결정하거나 제공해야 하는가 | `Task` |
| 어떤 데이터·규칙·기술로 해결했는가 | `Action` |
| 어떤 수치와 운영 가치가 만들어졌는가 | `Result` |

브리프 상단에는 다음 상태를 명시한다.

```text
문서 유형: 자체 정의 분석 브리프
실제 요청자: 없음
가상 활용 대상: 맵 QA 또는 라이브 운영
근거: 공개 데이터와 공개 PUBG 운영 사례
주의: KRAFTON 내부 요청서나 실제 업무 절차를 재현한 문서가 아님
```

분석 브리프는 임시 버전으로 시작할 수 있다. 프로파일링 전에는 확인되지 않은
컬럼, 품질 규칙과 임계값을 확정하지 않고 `미확정` 또는 `가정`으로 표시한다.
실제 데이터 분포를 확인한 뒤 지표와 범위를 갱신하고 변경 이유를 남긴다.

실제 요청자, 내부 우선순위, 승인 절차와 KPI 기준은 임의로 만들지 않는다.
공개 데이터를 사용해 Data Analytics Operation 업무를 연습하기 위해 직접
설정한 포트폴리오 시나리오라고 명시한다.

### 현재 시점의 STAR

아래 내용은 2026-07-31까지 실제로 확인하거나 수행한 범위만 사용한다.

#### Situation

> PUBG 공개 데이터에는 Erangel과 Miramar의 사망 원인과 피해자 위치가
> 포함되어 있었지만, 환경 사망이 여러 경기와 날짜에 걸쳐 반복되는 위치를
> 보여주는 운영 지표는 제공되지 않았다. 또한 6,537만 건의 사망 이벤트에는
> 맵 누락, 사용할 수 없는 `(0,0)` 좌표와 중복 등 분석 전에 확인해야 할 품질
> 문제가 있었다.

#### Task

> 실제 회사 요청이 없는 자체 정의 분석 브리프에서 맵 QA 활용 시나리오를
> 설정하고, `Falling`과 `Drown`이 반복되는 위치를 신뢰할 수 있게 선별할
> 데이터 품질 기준과 재현 가능한 처리 흐름을 설계하는 것을 목표로 했다.

#### Action

> 데이터 출처와 사용 범위를 확인한 뒤 DuckDB로 deaths 65,370,475행과
> aggregate 67,369,231행을 프로파일링했다. 완전 중복, 맵 누락, `(0,0)`,
> 좌표 범위, `match_id` 날짜 연결을 검사하고 각 제외 규칙과 행 수 대조식을
> 정의했다. 이후 100m·250m·500m 격자의 사망 수와 고유 경기 수를 일회성으로
> 집계해 공간 분석의 타당성을 먼저 확인했다.

#### Result

> 환경 사망 원본 후보 980,079행 중 모든 품질 규칙을 적용할 수 있는
> 793,356행을 확인하고, `980,079 = 중복 추가분 65 + 고유 제외 186,658
> + 분석 가능 793,356`으로 대조 차이를 0으로 만들었다. 예비 격자 분석에서는
> 네 개 맵·원인 조합 모두 다수 경기에서 반복되는 공간 집중 신호가 확인되어
> 후속 핫스팟 분석에 투자할 근거를 확보했다.

현재 Result는 프로파일링과 일회성 타당성 확인 결과다. 재사용 가능한 처리
파이프라인, PostgreSQL 적재, Superset 대시보드와 QA 점검 후보 보고서는 아직
완료하지 않았으므로 완료된 성과로 표현하지 않는다.

### 프로젝트 완료 후 목표 STAR

다음 문장은 구현 목표이며 현재 완료 사실이 아니다.

#### Situation

> 대규모 PUBG 사망 이벤트에는 환경 사망 위치가 있었지만, 데이터 품질 상태와
> 여러 경기·날짜의 반복성을 함께 보여주는 맵 QA용 운영 지표가 없었다.

#### Task

> 6,537만 건의 사망 이벤트를 전체 메모리에 적재하지 않고 처리해 신뢰 가능한
> 환경 사망 후보를 생성하고, 반복 위치를 QA가 우선순위로 검토할 수 있는
> 대시보드와 실행 가능한 보고서로 제공하고자 했다.

#### Action

> Python과 DuckDB로 스키마·중복·맵·좌표·날짜 품질 규칙을 자동화하고,
> 행별 품질 플래그와 제외 사유를 보존했다. 맵·격자·사망 원인별 사망 수,
> 고유 경기 수, 고유 날짜 수와 환경 사망 비율을 SQL로 계산하고, 실행 이력과
> 집계 결과를 PostgreSQL에 멱등 적재한 뒤 Superset 대시보드와 규칙 기반
> QA 후보 보고서를 구성했다.

#### Result

프로젝트 완료 후 다음 실제 측정값으로 작성한다.

- 처리 입력·출력·제외 행 수와 대조 차이
- 전체 실행 시간과 CSV·Parquet 비교 결과
- 탐지된 QA 점검 후보 수
- 후보가 반복된 최소·중앙 고유 경기 수와 날짜 수
- 대시보드 갱신과 재실행 결과
- pytest와 Ruff 결과

실제 맵 수정이나 환경 사망 감소를 측정하지 못하면 이를 Result에 포함하지 않는다.
