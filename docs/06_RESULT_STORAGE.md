# 결과 저장

> 문서 상태: 환경 사망 결과 저장 구현
>
> 구현 상태: 실행 이력, 품질 결과, 공간 집계의 PostgreSQL 적재 구현
>
> 저장 원칙: 상세 원본은 Parquet, 운영 및 집계 결과는 PostgreSQL

## 1. 목적

이 단계는 파이프라인 실행 이력, 품질 결과, 집계 지표와 보고서 메타데이터를 PostgreSQL에 안정적으로 저장한다.

PostgreSQL은 대시보드와 운영 조회에 필요한 작은 결과를 제공한다. 수천만 행의 원본 CSV와 상세 이벤트 전체를 PostgreSQL에 적재하는 것은 이 프로젝트의 기본 목표가 아니다.

## 2. 입력

이 단계는 [05_SQL_METRICS.md](05_SQL_METRICS.md)의 출력과 앞 단계의 운영 결과를 입력으로 받는다.

- 파이프라인 실행 이력
- 파일 및 배치 처리 결과
- 품질 검사 결과
- 스키마 변경 결과
- 게임 분석 지표 스냅샷
- 데이터 운영 지표 스냅샷
- 이후 생성될 AI 보고서 실행 메타데이터

모든 입력은 `run_id` 또는 이를 연결할 수 있는 식별자를 포함해야 한다.

## 3. 처리

### 저장 대상

| 논리 영역 | 저장 내용 | 주요 소비자 |
|---|---|---|
| 파이프라인 실행 | 상태, 입력·출력·실패 행 수, 시간, 오류 | 운영 대시보드, AI 보고서 |
| 입력 파일 | 파일 식별자, 크기, 체크섬, 처리 상태 | 파이프라인 재실행 |
| 품질 검사 | 규칙, 상태, 검사 건수, 오류율, 상세 | 운영 대시보드, AI 보고서 |
| 게임 지표 | 게임 분석 지표와 차원 | Gameplay 대시보드 |
| 운영 지표 | 처리량, 성공률, 실행 시간, 변화량 | Data Operations 대시보드 |
| 스키마 변경 | 이전·현재 버전, 변화 내용, 영향 | 운영 점검 |
| AI 보고서 | 입력 기준 실행, 생성 상태, 생성 시각, 오류 | 운영 이력 |

현재 구현한 물리 객체는 다음과 같다.

| 객체 | 기본 키 또는 멱등 키 | 내용 |
|---|---|---|
| `analytics_ops.pipeline_runs` | `run_id` | 매 실행의 상태, 건수, 시간, 오류 |
| `analytics_ops.quality_check_results` | `run_id + check_name` | 규칙별 검사 결과 |
| `analytics_ops.environmental_hotspots` | `batch_id + map + killed_by + grid_size_m + grid_x + grid_y` | 100m 공간 집계 |
| `analytics_ops.latest_pipeline_runs` | 뷰 | 파이프라인별 최신 실행 |
| `analytics_ops.latest_environmental_hotspots` | 뷰 | 최신 정상 공간 집계 |
| `analytics_ops.quality_run_summary` | 뷰 | 실행별 품질 요약 |

`source_files`, 스키마 변경과 AI 보고서 이력은 후속 범위로 남긴다.

### 적재 원칙

- 명시적인 기본 키 또는 고유 키를 사용한다.
- 동일 `run_id`와 결과 버전의 재적재는 중복 행을 만들지 않는다.
- 삽입과 갱신 기준을 테이블별로 정의한다.
- 원본의 상세 문자열이나 대용량 페이로드를 무조건 저장하지 않는다.
- 오류 상세는 운영에 필요한 범위로 제한한다.
- 시간 값은 일관된 시간대 기준으로 저장한다.
- 지표 정의와 품질 규칙 버전을 함께 저장한다.
- BI 조회용 뷰와 내부 적재 테이블을 구분한다.

### 트랜잭션 경계

한 배치의 관련 결과는 가능한 범위에서 일관된 상태로 저장한다.

현재 게시 상태 흐름은 다음과 같다.

```text
RUNNING
→ SUCCEEDED
또는
RUNNING
→ FAILED
```

`quality_status`는 `NOT_CHECKED`, `PASS`, `FAIL`로 별도 기록한다. 품질
`FAIL`이면 공간 집계를 쓰지 않고 실행 상태를 `FAILED`로 종료한다.

### 멱등 적재

최종 Parquet의 SHA-256으로 `batch_id`를 만든다. 같은 입력을 다시 실행해도
실행 이력은 새 `run_id`로 보존하지만, 공간 집계는 같은 `batch_id` 범위를
트랜잭션 안에서 삭제한 뒤 현재 결과를 삽입한다. 따라서 중복 행과 과거 실행의
잔여 격자가 생기지 않는다.

### 로컬 실행

```bash
cp .env.example .env
# POSTGRES_PASSWORD 변경
docker compose up -d postgres
python scripts/load_analytics_to_postgres.py
```

접속 비밀값은 `.env`에서 읽으며 출력하거나 저장소에 커밋하지 않는다.

### 계정 분리

PostgreSQL 계정은 적재와 조회 역할을 분리한다.

| 계정 | 역할 | 권한 범위 |
|---|---|---|
| `pubg_analytics` | 파이프라인 적재 및 스키마 관리 | 테이블 생성·변경, 결과 적재, 뷰 생성 |
| `analyst_ro` | 분석 및 운영 결과 조회 | `analytics_ops` 스키마 사용과 지정된 뷰 3개의 `SELECT`만 허용 |

`analyst_ro`는 `latest_environmental_hotspots`, `latest_pipeline_runs`,
`quality_run_summary`만 조회할 수 있다. 원본 테이블인
`environmental_hotspots`, `pipeline_runs`, `quality_check_results`에는 권한을
부여하지 않는다. 특히 환경 사망 집계는
`latest_environmental_hotspots`를 통해 마지막으로 성공한 게시 결과만 보게
강제한다. 새 테이블·뷰·시퀀스·함수가 생성되어도 조회 권한은 자동으로
추가되지 않는다.

Superset의 기존 연결 계정은 대시보드 중단을 피하기 위해 이번 변경에서
교체하지 않는다. 일반 분석·조회 쿼리부터 `analyst_ro`를 사용하고 Superset
연결 전환은 대시보드 호환성을 확인한 뒤 별도로 진행한다.

### 최초 정상 게시 결과

2026-07-31 실행 `151b8437-cb67-4a55-875f-12c4a6dbac42`에서 다음 결과를
기록했다.

| 항목 | 결과 |
|---|---:|
| 입력 Parquet | 793,356행 |
| 품질 검사 | 10개 `PASS` |
| 공간 집계 | 1,600행 |
| 파이프라인 상태 | `SUCCEEDED` |

개발 과정에서 발생한 품질 게이트 실패와 컬럼 매핑 실패도 `FAILED` 실행으로
남겼다. 실패 실행은 공간 집계를 게시하지 않았고 이후 정상 실행과 구분된다.

### 현재 BI 소비자

Superset은 원본 CSV나 상세 Parquet을 직접 조회하지 않고 다음 Dataset을
PostgreSQL에서 읽는다.

| Dataset | 대시보드 용도 |
|---|---|
| `latest_pipeline_runs` | 최신 실행 상태와 운영 KPI |
| `quality_run_summary` | 실행별 품질 상태 이력 |
| `latest_environmental_hotspots` | 상위 100m 격자 차트와 상세 표 |
| `quality_check_results` | 규칙별 실패 원인 확인 |

대시보드 메타데이터는 별도 `superset_metadata` 데이터베이스에 저장한다.
분석 결과와 BI 설정을 분리하되 두 데이터베이스는 Docker 볼륨으로 유지한다.

### 보존과 정리

- 원본과 Parquet 보존 정책은 파일 저장 영역에서 관리한다.
- PostgreSQL에는 운영 조회에 필요한 이력을 보존한다.
- 오래된 실행 상세와 집계 스냅샷의 보존 기간은 별도로 정한다.
- 삭제 또는 정리 작업도 실행 이력과 대상 범위를 남긴다.

## 4. 출력

이 단계의 출력은 Superset과 보고서 생성기가 조회할 수 있는 PostgreSQL 테이블과 뷰다.

다음 조회 요구를 지원해야 한다.

- 최근 파이프라인 실행 상태
- 마지막 정상 갱신 시각
- 실행별 입력·출력·실패 행 수
- 품질 상태와 실패 규칙
- 데이터량 변화
- 게임 지표의 최신 스냅샷
- 스키마 변경 이력
- AI 보고서 생성 성공과 실패

PostgreSQL 조회 결과는 [07_BI_DASHBOARD.md](07_BI_DASHBOARD.md)의 입력이 된다. 품질 결과와 운영 지표는 [08_AI_REPORT_AUTOMATION.md](08_AI_REPORT_AUTOMATION.md)에서도 사용한다.

## 5. 사용 기술

- PostgreSQL
- SQL
- Python 3.12 데이터베이스 적재 코드
- Docker Compose
- DuckDB에서 계산한 집계 결과
- pytest

데이터베이스 접속 정보는 환경변수로 전달하며 코드나 문서에 비밀값을 기록하지 않는다.

## 6. 성공 조건

- 원본 상세 데이터와 PostgreSQL 저장 결과가 명확히 구분된다.
- 실행, 품질, 지표, 스키마, AI 이력이 `run_id`로 연결된다.
- 동일 배치 재적재가 중복 결과를 만들지 않는다.
- 실패한 적재가 성공 상태로 기록되지 않는다.
- Superset이 필요한 결과를 원본 CSV 없이 조회할 수 있다.
- 최근 정상 상태와 과거 실패 이력을 모두 조회할 수 있다.
- 테이블과 인덱스가 실제 조회 패턴을 지원한다.

## 7. 실패 가능성

- PostgreSQL 연결 또는 인증이 실패할 수 있다.
- 일부 테이블만 적재되어 배치 상태가 불일치할 수 있다.
- 고유 키가 부족해 중복 행이 생길 수 있다.
- JSON 또는 오류 상세가 지나치게 커질 수 있다.
- 잘못된 시간대 처리로 최신 실행 판정이 틀릴 수 있다.
- 스키마 마이그레이션과 애플리케이션 버전이 맞지 않을 수 있다.
- Superset 조회가 적재 테이블에 과도한 부하를 줄 수 있다.

## 8. 확인 및 복구

- 적재 전후 행 수와 영향받은 행 수를 기록한다.
- 트랜잭션 실패 시 성공 상태를 남기지 않는다.
- 멱등 키로 동일 결과를 안전하게 재적재한다.
- 부분 적재가 발생하면 `run_id` 기준으로 상태를 확인하고 재처리한다.
- 스키마 변경은 마이그레이션 이력과 함께 관리한다.
- 분석·조회 쿼리는 조회 전용 계정을 사용하고 Superset 계정 전환은 별도로 검증한다.
- 연결 실패 시 Parquet과 구조화된 로컬 결과를 보존해 재적재할 수 있게 한다.

## 9. 채용공고 요구사항과의 연결

- 분석 결과와 운영 이력의 관계형 데이터 모델링
- SQL 기반 적재, 갱신, 조회 설계
- 대규모 원본과 서빙 데이터의 저장소 분리
- 배치 재실행과 중복 방지를 고려한 운영 설계
- BI와 보고서를 위한 안정적인 데이터 제공
- 실패 복구와 실행 추적

## 10. 미확정 사항

- 실행 및 품질 이력 보존 기간
- Superset 연결을 조회 전용 계정으로 전환할 시점과 호환성
- 원본 배치 수준 `WARNING` 임계치
- 스키마 변경 및 AI 보고서 이력 테이블
- 운영 규모 증가 시 파티셔닝 필요 여부
