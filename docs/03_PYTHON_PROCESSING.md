# Python 데이터 처리 및 자동화

> 문서 상태: 구현 진행
>
> 구현 상태: 환경 사망 정제·날짜 연결·Parquet 출력 1차 구현 완료
>
> 선행 조건: 실제 데이터 프로파일링 완료

## 1. 목적

이 단계는 승인된 원본 파일을 반복 가능하고 추적 가능한 방식으로 정제해
분석용 데이터를 생성한다. 현재 1차 분석 입력을 Parquet으로 생성하지만,
CSV와의 파일 크기 및 반복 조회 시간 비교 전에는 성능 개선 효과를 확정하지
않는다.

대규모 CSV를 메모리에 한 번에 적재하지 않고 처리하며, 동일 입력을 재실행해도 결과가 중복되지 않도록 한다. 각 실행의 입력 행 수, 출력 행 수, 실패 수, 소요 시간과 실패 원인을 기록한다.

## 2. 입력

이 단계는 [02_DATA_PROFILING.md](02_DATA_PROFILING.md)의 출력을 입력으로 받는다.

- 승인된 원본 파일과 `source_file_id`
- 파일 및 컬럼 프로파일
- 실제 데이터 사전 초안
- 확정된 타입 변환 규칙
- 키 후보와 중복 판정 후보
- 시간 파싱 규칙
- 품질 검사 후보

프로파일링에서 확인되지 않은 컬럼이나 타입을 처리 코드에서 임의로 생성하지 않는다.

## 3. 처리

### 현재 구현 상태

첫 처리 코드는 `scripts/build_environmental_deaths.py`에 작성했다.
DuckDB의 `read_csv_auto`와 파일 glob을 사용해 deaths CSV 5개를 하나의
입력처럼 조회하고, 현재 분석 범위인 `Falling`과 `Drown`을 정제한다.
aggregate CSV 5개는 `match_id`당 날짜가 한 행이 되도록 축약한 뒤
`LEFT JOIN`해 조인으로 사망 행이 증가하지 않는지 검사한다.

2026-07-31 실행 결과는 다음과 같다.

| `killed_by` | 원본 후보 행 수 |
|---|---:|
| `Falling` | 708,367 |
| `Drown` | 271,712 |
| 합계 | 980,079 |

이 값은 프로파일링 기준선과 일치한다. 현재 구현 범위는 다음과 같다.

- deaths CSV 5개가 glob 입력에 포함된다.
- 환경 사망 원인 필터가 `Falling`과 `Drown`만 선택한다.
- 품질 규칙 적용 전 원본 후보 980,079행을 재현한다.
- 12개 원본 컬럼 완전 중복 추가분 65행을 제거한다.
- 맵, `match_id`, 좌표, `0,0`, 공식 좌표 범위 품질 상태를 계산한다.
- aggregate의 기존 날짜가 일관된 `match_id`만 연결한다.
- 최종 분석 가능 793,356행을 생성한다.
- 단계별 제외 건수와 실행 시간을 콘솔에 출력한다.
- 결과를 `data/processed/environmental_deaths.parquet`으로 교체 저장한다.

2026-07-31 전체 입력 실행에서 출력 크기는 37.58 MB, 실행 시간은
19.17초였다. 품질 결과와 실행 이력의 PostgreSQL 영속화, 실패 행 격리,
CSV 대비 Parquet 조회 성능 측정은 아직 구현하지 않았다.

### 신규 입력 파일 탐색

- 입력 디렉터리에서 허용된 파일 패턴만 찾는다.
- 파일 경로, 크기, 수정 시각, 체크섬으로 입력을 식별한다.
- 입력 인벤토리와 비교해 신규, 변경, 처리 완료 파일을 구분한다.
- 이미 성공한 동일 파일은 기본적으로 다시 처리하지 않는다.
- 강제 재처리는 새로운 실행 이력으로 남기고 기존 결과와 충돌하지 않게 한다.

### 파일과 스키마 검사

- 지원 형식인지 확인한다.
- 헤더와 컬럼 구성이 승인된 스키마와 일치하는지 확인한다.
- 필수 컬럼 누락과 예상하지 못한 컬럼 추가를 기록한다.
- 타입 변환 불가 값을 실패 또는 격리 대상으로 분류한다.
- 스키마 변경 여부를 실행 이력에 연결한다.

### 대규모 데이터 처리

- DuckDB로 CSV를 직접 조회하거나 제한된 청크 단위로 처리한다.
- 전체 파일을 pandas DataFrame 하나로 올리지 않는다.
- 필요한 컬럼만 읽고 가능한 연산은 SQL로 푸시다운한다.
- 입력 파일 단위 또는 명확한 파티션 단위로 결과를 생성한다.
- 중간 결과와 최종 결과를 구분한다.

### 정제와 타입 정규화

실제 프로파일링 결과를 기준으로 다음 처리를 설계한다.

- 빈 문자열과 NULL 표현 정규화
- 숫자, 날짜, 불리언, 카테고리 타입 변환
- 문자열 앞뒤 공백과 인코딩 문제 처리
- 허용되지 않은 변환 실패 값 격리
- 분석에 불필요한 식별 가능 값의 공개용 결과 제외

원본 값 수정이 필요한 경우 원본 컬럼을 덮어쓰지 않고 정제 규칙과 변경 건수를 추적할 수 있게 한다.

### 파생값 계산

파생값은 실제 컬럼과 단위가 확인된 경우에만 추가한다.

모든 파생값은 다음 정보를 문서화한다.

- 이름
- 입력 컬럼
- 계산식
- NULL 처리
- 단위
- 계산 실패 조건
- 사용 지표

### CSV에서 Parquet 변환

- 정제 결과를 Parquet으로 저장한다.
- 파일 또는 분석에 유용한 기준으로 파티션을 설계한다.
- 압축 코덱과 파일 크기 목표를 기록한다.
- 임시 경로에 쓴 뒤 완료된 파일만 최종 경로로 이동한다.
- 출력 행 수와 파일 크기를 입력과 대조한다.

### SQL 실행 순서 제어

예정 실행 순서는 다음과 같다.

```text
입력 발견
→ 입력 승인 확인
→ 스키마 검사
→ 정제 및 타입 변환
→ Parquet 생성
→ 출력 검증
→ 품질 검사 호출
→ 품질 게이트 통과 시 지표 SQL 실행
→ 결과 저장
```

각 단계는 이전 단계의 성공 상태를 확인한 후 실행한다.

### 실행 이력과 멱등성

각 실행에 다음 항목을 기록한다.

| 항목 | 설명 |
|---|---|
| `run_id` | 파이프라인 실행 식별자 |
| `batch_id` | 입력 배치 식별자 |
| `source_file_id` | 입력 파일 식별자 |
| `status` | 실행 상태 |
| `input_rows` | 읽은 행 수 |
| `output_rows` | 생성한 행 수 |
| `failed_rows` | 처리 실패 행 수 |
| `started_at`, `finished_at` | 시작 및 종료 시각 |
| `duration_seconds` | 소요 시간 |
| `error_type`, `error_message` | 실패 원인 |
| `output_path` | 생성된 Parquet 위치 |

중복 방지 키는 데이터셋 버전, 파일 체크섬, 처리 로직 버전을 조합하는 방향으로 설계하되 구현 전에 확정한다.

## 4. 출력

이 단계의 출력은 다음과 같다.

- 정제된 상세 이벤트 Parquet
- 정제된 경기 또는 플레이어 집계 Parquet
- 처리 성공 및 실패 파일 목록
- 격리된 실패 행 또는 실패 원인 요약
- 입력·출력·실패 행 수
- 실행 시간과 실행 상태
- 출력 파일 체크섬 또는 크기
- 적용한 스키마 및 처리 로직 버전

정제 Parquet과 실행 이력은 [04_DATA_QUALITY.md](04_DATA_QUALITY.md)의 입력이 된다. 품질 검사가 끝나기 전에는 분석 지표용 확정 데이터로 게시하지 않는다.

## 6. 성공 조건

- 승인된 입력 파일만 처리한다.
- 대규모 CSV를 전체 메모리에 적재하지 않는다.
- 입력·출력·실패 행 수가 기록된다.
- 처리 시간이 측정된다.
- 변환 실패를 무시하지 않고 원인을 기록한다.
- 성공한 출력만 최종 Parquet 위치에 노출된다.
- 동일 입력의 재실행이 중복 결과를 만들지 않는다.
- 스키마와 처리 로직 버전이 추적된다.
- 출력이 품질 검사 단계에서 다시 조회 가능하다.

## 7. 실패 가능성

- 신규 파일 탐색 패턴이 필요한 파일을 누락할 수 있다.
- 파일 일부가 기록 중인 상태에서 처리를 시작할 수 있다.
- CSV 파싱 또는 타입 변환이 실패할 수 있다.
- 임시 파일이 남거나 최종 파일이 불완전할 수 있다.
- 디스크 공간 부족으로 Parquet 쓰기가 실패할 수 있다.
- 재실행 시 이전 결과와 충돌할 수 있다.
- 코드 버전이 달라졌는데 같은 결과로 인식할 수 있다.
- PostgreSQL 이력 기록 실패와 Parquet 생성 성공이 불일치할 수 있다.

## 8. 확인 및 복구

- 파일 크기와 체크섬이 안정된 입력만 처리한다.
- 단계별 상태와 마지막 성공 지점을 기록한다.
- 임시 파일은 성공 상태로 취급하지 않는다.
- 실패 파일은 원본을 수정하지 않고 다시 처리할 수 있게 한다.
- 행 수 대조가 실패하면 품질 검사 단계로 넘기지 않는다.
- PostgreSQL 기록이 실패하면 생성 결과를 미게시 상태로 유지한다.
- 재실행은 동일한 `source_file_id`와 로직 버전을 확인해 멱등 처리한다.
- 복구 후 입력·출력 행 수와 출력 체크섬을 다시 기록한다.
