# 데이터 품질 검사

> 문서 상태: 환경 사망 규칙 및 최종 게시 품질 게이트 구현
>
> 구현 상태: 환경 사망 정제, 최종 Parquet 자동 판정, PostgreSQL 영속화 구현
>
> 규칙 상태: `DQ-SCHEMA-001`, `DQ-DATE-001`, `DQ-MAP-001`, `DQ-COORD-001`, `DQ-COORD-002`, `DQ-DUP-001` 확정, 환경 사망 범위 처리 구현

## 1. 목적

이 단계는 정제된 데이터를 SQL 지표 계산에 사용해도 되는지 일관된 기준으로 판단한다.

Python과 SQL이 품질 상태를 계산하고, Superset과 AI는 그 결과를 표시하거나 요약한다. BI 또는 LLM이 데이터 정상 여부를 새로 판단하지 않는다.

### 현재 규칙 현황

원본 전체에서 규칙 근거와 영향 행 수를 측정해 품질 계약을 확정했다. 원본은
변경하지 않고 환경 사망 범위에서 규칙을 적용한 Parquet을 생성한다. 게시
직전에는 최종 Parquet에 같은 핵심 규칙을 다시 적용하고 규칙별 결과를
PostgreSQL에 영속화한다.

| 규칙 | 내용 | 측정 결과 | 정의 | 처리 구현 |
|---|---|---:|---|---|
| `DQ-SCHEMA-001` | 파일 그룹별 컬럼·순서·타입 일치 | 불일치 0건 | 확정 | 검사 스크립트 구현 |
| `DQ-DATE-001` | 기존 `match_id`로 연결된 날짜만 사용 | 연결 실패 2,609행 | 확정 | 환경 사망 범위 구현 |
| `DQ-MAP-001` | `map` 결측을 맵 기반 분석에서 제외 | 783,392행 | 확정 | 환경 사망 범위 구현 |
| `DQ-COORD-001` | 공식 좌표 범위 밖 공간 분석 제외 | 전체 71행, 환경 사망 25행 | 확정 | 환경 사망 범위 구현 |
| `DQ-COORD-002` | 환경 사망의 정확한 `0,0` 공간 분석 제외 | `Falling` 14,513행, `Drown` 164,124행 | 확정 | 환경 사망 범위 구현 |
| `DQ-DUP-001` | 12개 컬럼 완전 중복의 추가 사본 제외 | 초과 211행 | 확정 | 환경 사망 범위 구현 |

현재 측정값을 단순히 더해 최종 제외 행 수로 사용하면 안 된다. 예를 들어
`Drown`, `0,0`, 완전 중복을 동시에 만족하는 같은 행이 여러 규칙에 포함될 수
있다. 정제 단계에서 행별 품질 플래그를 함께 계산한 뒤 규칙 간 중복을 제거한
최종 분석 가능 행 수를 측정해야 한다.

모든 확정 규칙을 함께 적용한 현재 결과:

```text
원본 환경 사망: 980,079
완전 중복 초과: 65
중복 제거 후 고유 제외: 186,658
최종 분석 가능: 793,356
건수 대조 차이: 0
```

2026-07-31 처리 실행에서 이 기준과 같은 793,356행을
`data/processed/environmental_deaths.parquet`으로 생성했다. 파일 크기는
비식별 `event_id` 추가 후 51.48 MB, 실행 시간은 23.82초였다.

### 최종 게시 품질 게이트

`sql/final_environmental_quality_checks.sql`은 최종 Parquet에 다음 10개
검사를 실행한다. 허용 오류 건수는 현재 모두 0이며 하나라도 실패하면
`environmental_hotspots` 게시를 차단한다.

- 전체 게시 적격성
- 비식별 `event_id` 존재
- 지원 맵
- `match_id` 존재
- 좌표 NULL
- 정확한 `(0, 0)`
- 좌표 범위
- 기존 aggregate 날짜 연결
- 환경 사망 원인
- 최종 이벤트 키 중복

최종 분석 컬럼만으로 중복을 다시 정의하지 않는다. 서로 다른 피해자가 같은
경기와 좌표에서 같은 원인으로 사망하면 분석 컬럼이 같아도 서로 다른 사건일
수 있기 때문이다. `event_id`는 원본 12개 컬럼으로 완전 중복을 제거한 직후
생성하고, 이름 등 원본 상세값은 최종 Parquet에 남기지 않는다. 게시 단계의
중복 검사는 이 `event_id`가 반복되는지만 확인한다.

`scripts/load_analytics_to_postgres.py`는 규칙별 검사 행 수, 오류 수, 오류율,
규칙 버전을 `analytics_ops.quality_check_results`에 기록한다. 품질 계산은
DuckDB가 담당하고 PostgreSQL은 결과와 실행 상태만 보존한다.

2026-07-31 정상 게시 실행에서 793,356행에 대한 10개 검사가 모두
`PASS`였고, 공간 집계 1,600행의 게시를 허용했다.

## 3. 처리

### DQ-SCHEMA-001: 입력 파일 스키마 일치

같은 파일 그룹에 속한 모든 CSV는 컬럼 이름, 순서와 추론 타입이 같아야 한다.

처리 원칙:

- deaths는 12개, aggregate는 15개 컬럼을 기대한다.
- 파일별 전체 값을 대상으로 DuckDB 추론 타입을 비교한다.
- 컬럼 추가·삭제·순서 변경·타입 변화가 있으면 자동 결합 전에 실패시킨다.
- 타입을 강제로 맞춰 오류를 숨기지 않고 차이를 실행 결과에 기록한다.

현재 deaths 5개와 aggregate 5개에서 불일치는 0건이었다.

### DQ-DATE-001: 기존 경기 날짜만 사용

환경 사망이 여러 날짜에 걸쳐 반복되는지 측정할 때 날짜를 추정하거나 새로
생성하지 않는다. deaths 데이터에는 날짜 컬럼이 없으므로 aggregate 데이터에
실제로 존재하는 `date`를 정확히 같은 `match_id`로 연결한 경우에만
`match_date`로 사용한다.

처리 원칙:

- aggregate의 `match_id`별 `date` 고유값 개수를 먼저 검사한다.
- 한 `match_id`에 날짜가 하나만 존재할 때만 경기 단위 `dim_match`에 포함한다.
- deaths와 `dim_match`는 정확히 같은 `match_id`로 연결한다.
- 연결된 기존 `aggregate.date`는 출처를 명확히 하기 위해 `match_date`라는
  이름으로 사용한다.
- 현재 날짜, 파일명, 행 순서, 인접 경기, 보간값, 최솟값 또는 최댓값으로
  날짜를 채우지 않는다.
- 연결되지 않은 행은 `match_date = NULL`, `is_date_eligible = false`,
  `date_quality_reason = 'DATE_NOT_FOUND'`로 기록한다.
- 한 `match_id`에 여러 날짜가 발견되면 임의의 날짜를 고르지 않고
  `date_quality_reason = 'MATCH_DATE_CONFLICT'`로 격리한다.
- 여러 날짜에 걸친 반복성을 측정하는 본 분석에는
  `is_date_eligible = true`인 행만 포함한다.
- 제외된 행도 원본에서 삭제하지 않고 품질 결과와 제외 건수를 남긴다.

현재 전체 프로파일링에서 확인한 결과:

| 항목 | 확인값 |
|---|---:|
| 전체 deaths 행 | 65,370,475 |
| 기존 경기 날짜와 연결된 deaths 행 | 65,367,866 |
| 날짜 연결 실패 deaths 행 | 2,609 |
| 날짜 연결률 | 약 99.996% |
| 여러 aggregate 날짜를 가진 `match_id` | 0 |

따라서 환경 사망의 날짜별 반복성 분석은 65,367,866개의 날짜 연결 가능
deaths 행 범위 안에서 수행한다. 연결되지 않은 2,609행에는 날짜를 만들어
넣지 않고 날짜 기반 지표에서 제외한다. 배치 전체를 `PASS`, `WARNING`,
`FAIL` 중 무엇으로 판정할지에 대한 허용 임계치는 후속 규칙 설계에서
확정한다.

### DQ-MAP-001: map 결측의 맵 기반 분석 제외

deaths의 `map`이 NULL이면 에란겔과 미라마를 구분할 수 없으므로 맵별 공간
분석에 사용하지 않는다.

처리 원칙:

- NULL을 에란겔 또는 미라마로 임의 입력하지 않는다.
- 좌표, 파일명, 날짜 또는 전체 맵 비율로 맵을 추정하지 않는다.
- 해당 행은 `is_spatial_eligible = false`,
  `spatial_quality_reason = 'MISSING_MAP'`으로 기록한다.
- 맵이 필요 없는 전체 사망 원인 건수에는 목적을 명시한 경우 포함할 수 있다.
- 원본 행과 NULL 값은 삭제하거나 변경하지 않는다.

현재 `map` NULL은 783,392행과 8,893개 경기에 존재한다. 해당 경기에서는
모든 deaths 행의 `map`이 NULL이어서 같은 경기의 다른 행으로 복구 가능한
건수는 0이다. 환경 사망 중에는 `Drown` 3,483행과 `Falling` 6,970행이
해당한다.

한 `match_id`에서 서로 다른 두 맵이 발견된 경우는 0건이었다. 향후 배치에서
여러 맵이 발견되면 임의로 하나를 선택하지 않고 `MAP_CONFLICT`로 격리한다.

### DQ-COORD-001: 공식 맵 범위 밖 좌표 제외

에란겔과 미라마의 피해자 X·Y 좌표는 공식 PUBG Telemetry Objects 문서에
기재된 `0~816,000cm`를 공간 분석 유효 범위로 사용한다.

처리 원칙:

- X 또는 Y가 `0`보다 작거나 `816,000`보다 크면
  `spatial_quality_reason = 'OUT_OF_MAP_BOUNDS'`로 기록한다.
- 해당 행은 `is_spatial_eligible = false`로 분류하고 환경 사망 핫스팟
  분석에서 제외한다.
- 원본 행과 원본 좌표는 삭제하거나 변경하지 않는다.
- 음수를 `0`으로, 상한 초과값을 `816,000`으로 강제 보정하지 않는다.
- 위치를 사용하지 않는 전체 사망 원인 집계에는 목적을 명시한 경우 사용할 수
  있지만 공간 지표에는 사용하지 않는다.
- 범위 밖 좌표를 데이터 수집 오류나 게임 버그로 자동 판정하지 않는다.

전체 deaths 65,370,475행 중 범위 밖 좌표는 71행으로 0.000108612%이며,
이 중 `Falling`과 `Drown`은 25행이다. `0,0`은 공식 숫자 범위 안이므로
이 규칙에 포함하지 않고 별도 품질 규칙으로 판단한다.

### DQ-COORD-002: 환경 사망의 정확한 `0,0` 위치 제외

공식 좌표 체계에서 `0,0`은 맵 왼쪽 위 원점이지만 현재 데이터에서는 실제
위치 분포로 보기 어려운 정확한 `0,0` 집중이 확인됐다.

처리 원칙:

- `killed_by`가 `Falling` 또는 `Drown`이고 피해자 X·Y가 모두 정확히
  0이면 `spatial_quality_reason = 'INVALID_OR_UNAVAILABLE_POSITION'`으로
  기록한다.
- 해당 행은 `is_spatial_eligible = false`로 분류하고 환경 사망 핫스팟
  분석에서 제외한다.
- 전체 사망 원인 건수와 제외율 계산에는 원본 행을 보존한다.
- `0,0`을 다른 좌표로 보간하거나 맵 안의 임의 위치로 이동하지 않는다.
- `0,0`을 접속 종료, 잠수 플레이 또는 게임 오류로 자동 분류하지 않는다.

판단 근거:

- 전체 `Drown` 271,712행 중 164,124행, 60.403663%가 정확한 `0,0`이다.
- `0,0 Drown`은 92,002개 경기에 걸쳐 나타났다.
- 원점 10m 이내에는 `0,0`을 제외한 비영점 `Drown`이 0행이고, 100m
  이내에는 2행뿐이었다.
- `0,0`의 `time` 중앙값은 170이고 25~75백분위가 168~176인 반면,
  비영점의 중앙값은 674로 분포가 크게 달랐다.
- 다섯 원본 CSV 모두 `Drown`의 `0,0` 비율이 약 60%였다.

이 규칙은 현재 환경 사망 공간 분석에 적용하는 프로젝트 규칙이다. 다른 분석
목적에서 모든 `0,0`을 결측으로 일반화하려면 별도 근거가 필요하다.

### DQ-DUP-001: 12개 원본 컬럼 완전 중복 제거

deaths의 12개 원본 컬럼이 모두 같은 행은 원본 중복으로 분류한다.

제외하는 이유:

- 같은 경기, 피해자, 시각, 사망 원인, 위치와 killer 정보가 모두 같아 서로
  다른 두 사건이라고 해석할 추가 근거가 없다.
- 그대로 집계하면 실제 정보는 한 건인데 `COUNT(*)` 기반 사망 건수는 두 건
  또는 세 건으로 증가한다.
- 해당 좌표 격자의 사망 수와 환경 사망 비율이 실제 기록보다 커질 수 있다.
- 중복 사본은 새로운 분석 정보를 제공하지 않으면서 원인별·위치별 분포만
  왜곡한다.

`COUNT(DISTINCT match_id)`처럼 경기 수만 세는 지표에는 영향이 없을 수 있지만,
사망 이벤트 수와 위치 밀도를 계산하는 현재 분석에는 직접 영향을 준다. 전체
대비 비율은 약 0.000323%로 매우 작지만, 확인된 중복을 그대로 두어야 할
분석상 이점은 없다.

처리 원칙:

- 원본 CSV는 수정하거나 중복 행을 삭제하지 않는다.
- 분석용 출력에서는 동일한 12개 컬럼 조합을 한 번만 사용한다.
- 중복된 추가 행은 `duplicate_quality_reason = 'EXACT_DUPLICATE'`로
  집계하고 제외 행 수를 실행 이력에 기록한다.
- 입력 행 수는 중복 제거 후 출력 행 수와 완전 중복 제외 행 수의 합과
  일치해야 한다.
- 조인 전후에도 같은 검사를 실행해 파이프라인이 새 중복을 만들지 확인한다.
- `match_id`만 같은 행은 중복으로 분류하지 않는다.

현재 전체 원본에서 완전 중복 193개 그룹과 초과 211행이 확인됐다. 모든
그룹은 동일 파일 안에 있었으며 파일 간 중복 그룹은 0이었다. 환경 사망
중에서는 `Drown`에 초과 65행이 있었고 `Falling` 완전 중복은 없었다.

`match_id + victim_name + time + killed_by`가 같지만 상세값이 다른 이벤트
후보는 이 규칙으로 제거하지 않는다. 해당 후보의 의미와 처리 규칙은 별도로
확정한다.

### 검사 범주

| 검사 범주 | 확인 내용 | 초기 판정 방향 |
|---|---|---|
| 필수 컬럼 | 분석과 조인에 필요한 컬럼 존재 여부 | 누락 시 `FAIL` 후보 |
| NULL | 필수 값과 일반 값의 NULL 건수 및 비율 | 컬럼별 기준 필요 |
| 중복 | 정의된 키 기준 중복 행 또는 이벤트 | 허용 여부와 기준 필요 |
| 참조 무결성 | 이벤트가 유효한 경기 또는 상위 엔터티를 참조하는지 | 오류 비율 기준 필요 |
| 시간 범위 | 파싱 실패, 미래 시각, 허용 범위 밖의 시각 | 실제 수집 기간 필요 |
| 좌표 범위 | 좌표 후보가 확인된 맵 또는 단위 범위에 있는지 | 컬럼과 단위 확인 필요 |
| 신규 카테고리 | 기준선에 없는 맵, 모드, 원인 등의 등장 | 일반적으로 `WARNING` 후보 |
| 스키마 변경 | 컬럼 추가·삭제·타입 변화·순서 변화 | 영향도에 따라 판정 |
| 배치 데이터량 | 전회 또는 기준선 대비 급감·급증 | 기준선과 임계값 필요 |
| 처리 건수 대조 | 입력, 출력, 실패, 격리 건수의 일관성 | 불일치 시 `FAIL` 후보 |

### 판정 상태

| 상태 | 의미 | 후속 처리 |
|---|---|---|
| `PASS` | 정의된 품질 기준을 충족 | 지표 계산 허용 |
| `WARNING` | 분석은 가능하지만 확인이 필요한 변화 또는 오류가 존재 | 경고를 포함해 지표 계산 가능 |
| `FAIL` | 결과 신뢰성에 중대한 문제가 있어 게시하면 안 됨 | 지표 게시 중단 및 조치 필요 |

각 규칙의 상태는 오류 건수, 오류 비율, 비즈니스 영향도를 근거로 계산한다. 임계값은 실제 프로파일링 결과와 처리 목표를 검토한 뒤 확정한다.

### 실행 절차

```text
정제 출력 존재 확인
→ 스키마 검사
→ 행 수준 검사
→ 관계 검사
→ 범위 및 카테고리 검사
→ 배치 변화량 검사
→ 규칙별 상태 계산
→ 배치 전체 품질 상태 계산
→ PostgreSQL 적재 대상 생성
```

배치 전체 상태는 가장 심각한 규칙 상태를 기본값으로 사용하되, 예외 규칙이 필요한지는 구현 전에 결정한다.

### 결과 구조

각 검사 결과에 다음 항목을 포함한다.

| 필드 | 설명 |
|---|---|
| `run_id` | 파이프라인 실행 식별자 |
| `batch_id` | 검사 배치 식별자 |
| `check_name` | 검사 이름 |
| `status` | `PASS`, `WARNING`, `FAIL` |
| `checked_rows` | 검사 대상 행 수 |
| `error_count` | 오류 건수 |
| `error_rate` | 오류 비율 |
| `checked_at` | 검사 시각 |
| `details` | 기준, 관측값, 영향에 대한 구조화된 상세 |
| `rule_version` | 적용 규칙 버전 |

날짜가 연결된 분석용 행에는 다음 출처 및 적격성 필드도 포함한다.

| 필드 | 설명 |
|---|---|
| `match_date` | 정확히 일치한 `match_id`에서 가져온 기존 `aggregate.date` |
| `date_source` | 날짜 출처. 정상 연결 시 `aggregate` |
| `is_date_eligible` | 날짜 기반 분석에 사용할 수 있는지 여부 |
| `date_quality_reason` | 날짜 연결 실패 또는 충돌로 제외된 이유 |

## 4. 출력

이 단계의 출력은 다음과 같다.

- 규칙별 품질 검사 결과
- 배치 전체 품질 상태
- 실패 또는 경고 규칙 목록
- 오류 건수와 오류 비율
- 스키마 변경 내역
- 데이터량 변화 결과
- SQL 지표 계산 허용 여부

`PASS`와 정책상 허용된 `WARNING` 배치는 [05_SQL_METRICS.md](05_SQL_METRICS.md)의 입력이 된다. `FAIL` 배치는 원인을 해결하거나 승인된 예외가 기록되기 전까지 지표 게시를 차단한다.

## 5. 사용 기술

- DuckDB SQL
- Python 3.12
- Parquet
- PostgreSQL
- pytest

핵심 품질 규칙은 작은 고정 입력으로 재현 가능한 pytest를 작성한다. 규칙 실행과 상태 집계를 분리해 테스트한다.

## 6. 성공 조건

- 모든 품질 규칙에 이름, 목적, 대상, 계산식, 판정 기준이 있다.
- 검사 행 수, 오류 건수, 오류 비율이 기록된다.
- 검사 실행 시각과 규칙 버전이 기록된다.
- `PASS`, `WARNING`, `FAIL`의 후속 동작이 명확하다.
- `FAIL` 배치의 지표 게시가 차단된다.
- 스키마 변경과 신규 카테고리가 탐지된다.
- 핵심 규칙이 pytest로 검증된다.
- 동일 입력과 규칙 버전은 일관된 결과를 낸다.

## 7. 실패 가능성

- 잘못된 임계값으로 정상 데이터를 실패 처리할 수 있다.
- 느슨한 규칙으로 실제 오류를 통과시킬 수 있다.
- NULL 또는 중복 정의가 데이터 의미와 맞지 않을 수 있다.
- 참조 무결성 검사 조인 비용이 클 수 있다.
- 기준선 자체가 편향되거나 불완전할 수 있다.
- 신규 카테고리를 오류로 잘못 분류할 수 있다.
- 일부 규칙 실패가 전체 품질 실행을 중단시킬 수 있다.
- 오류 상세에 식별 가능한 원문 값이 포함될 수 있다.

## 8. 확인 및 복구

- 각 규칙은 독립적으로 실행 결과를 남긴다.
- 규칙 실행 오류와 데이터 품질 오류를 다른 상태로 기록한다.
- `FAIL` 샘플은 공개하지 않고 제한된 로컬 위치에서 확인한다.
- 임계값 변경 시 규칙 버전을 올리고 과거 결과와 구분한다.
- 기준선 변경 이유와 승인자를 기록한다.
- 오탐으로 확인된 경우 데이터를 수정하기 전에 규칙과 근거를 검토한다.
- 수정 또는 재처리 후 동일 규칙을 다시 실행해 결과를 비교한다.

## 9. 채용공고 요구사항과의 연결

- 데이터 품질 검토와 오류 원인 분석
- 스키마와 이벤트 관계 이해
- SQL을 이용한 NULL, 중복, 조인, 범위 검사
- 배치 데이터량과 품질 성공률 모니터링
- 테스트 가능한 운영 규칙 설계
- 오류를 숨기지 않고 실행 이력으로 남기는 운영 태도

## 10. 미확정 사항

- 필수 컬럼
- NULL 허용 컬럼과 임계값
- 중복 판정 키
- 정상 시간 범위
- 좌표 컬럼, 단위, 맵별 허용 범위
- 카테고리 기준선
- 배치 급감·급증 임계값
- 배치 전체 상태 집계 규칙
- `WARNING` 상태에서 허용할 후속 처리
- `DATE_NOT_FOUND` 비율에 따른 배치 심각도 임계치
- 품질 결과 보존 기간
