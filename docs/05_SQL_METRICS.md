# SQL 지표

> 문서 상태: 초기 설계
>
> 구현 상태: 미구현
>
> 지표 상태: 실제 스키마 확인 후 확정

## 1. 목적

이 단계는 품질 게이트를 통과한 데이터에서 게임 분석 지표와 데이터 운영 지표를 SQL로 계산한다.

게임 분석 지표는 데이터의 활용 가능성을 보여주고, 데이터 운영 지표는 파이프라인이 최신 데이터를 정상적으로 처리했는지 보여준다. 후보 지표는 실제 컬럼, 단위, 조인 관계가 확인된 경우에만 구현 대상으로 확정한다.

## 2. 입력

이 단계는 [04_DATA_QUALITY.md](04_DATA_QUALITY.md)의 출력을 입력으로 받는다.

- 품질 게이트를 통과한 정제 Parquet
- `run_id`, `batch_id`
- 배치 전체 품질 상태
- 규칙별 품질 결과
- 실제 데이터 사전
- 확인된 키와 조인 관계
- 입력·출력·실패 행 수
- 이전 정상 배치의 운영 기준값

`FAIL` 상태의 배치는 기본적으로 지표 게시 대상에서 제외한다.

## 3. 처리

### 게임 분석 지표 후보

| 후보 지표 | 분석 질문 | 확정 전 확인 사항 |
|---|---|---|
| 맵별 경기 수 | 어떤 맵의 경기가 포함되어 있는가 | 맵과 경기 식별 컬럼 |
| 게임 모드별 경기 수 | 어떤 플레이 방식이 포함되어 있는가 | 모드 정의와 경기 식별 컬럼 |
| 무기별 처치 비율 | 사망 이벤트에서 각 원인이 차지하는 비율은 얼마인가 | 처치 원인 또는 무기 컬럼 |
| 경기당 평균 사망 이벤트 | 경기 하나에 평균 몇 개의 사망 이벤트가 있는가 | 경기 조인 키와 이벤트 정의 |
| 평균 교전 거리 | 위치 정보로 계산 가능한 평균 거리는 얼마인가 | 좌표 컬럼, 단위, 결측 처리 |

이 목록은 포트폴리오 방향을 설명하는 후보이며 현재 구현 완료 지표가 아니다.

각 지표를 확정할 때 다음 내용을 문서화한다.

- 지표 이름
- 분석 목적
- 계산 SQL
- 데이터 원천
- 집계 단위
- 필터 조건
- NULL 및 중복 처리
- 단위
- 갱신 주기
- 품질 의존성

### 데이터 운영 지표

| 운영 지표 | 계산 기준 |
|---|---|
| 배치별 입력 행 수 | 파이프라인 실행 이력의 입력 건수 |
| 배치별 출력 행 수 | 정제 완료 건수 |
| 실패 행 수와 실패율 | 처리 실패 또는 격리 건수 |
| 품질 검사 성공률 | 실행된 검사 중 `PASS` 비율 |
| 품질 상태별 건수 | `PASS`, `WARNING`, `FAIL` 검사 수 |
| NULL·중복·참조 오류 건수 | 규칙별 오류 건수 |
| 처리 시간 | 실행 시작과 종료 시각의 차이 |
| 데이터량 전회 대비 변화 | 현재 정상 배치와 이전 정상 배치의 건수 비교 |
| 마지막 정상 갱신 시각 | 최근 성공 및 품질 통과 실행 시각 |
| 스키마 변경 건수 | 배치에서 탐지된 스키마 변화 수 |

운영 지표는 원본 이벤트를 다시 해석하지 않고 실행 이력과 품질 결과를 집계한다.

### SQL 작성 원칙

- 지표별 집계 단위를 명시한다.
- 필터와 조인 조건을 SQL에 명시한다.
- 원본 전체를 PostgreSQL로 복사하지 않고 DuckDB가 Parquet을 직접 조회한다.
- 동일 배치 재실행 시 같은 지표 스냅샷이 중복되지 않게 한다.
- 현재 배치와 이전 정상 배치의 기준을 명확히 한다.
- `WARNING` 데이터 포함 여부를 지표 메타데이터에 표시한다.
- 계산 결과와 함께 분모, 대상 행 수, 실행 시각을 저장한다.

## 4. 출력

이 단계의 출력은 PostgreSQL 적재가 가능한 지표 스냅샷이다.

공통 출력 항목은 다음과 같다.

| 필드 | 설명 |
|---|---|
| `run_id` | 지표를 생성한 실행 |
| `metric_name` | 지표 이름 |
| `metric_group` | `gameplay` 또는 `operations` |
| `dimension_key` | 맵, 모드 등 차원 식별값 |
| `metric_value` | 계산 결과 |
| `row_count` | 계산에 사용한 행 수 |
| `quality_status` | 입력 배치 품질 상태 |
| `calculated_at` | 계산 시각 |
| `metric_version` | 계산 정의 버전 |

실제 물리 스키마는 지표별 자료형과 조회 패턴을 확인한 뒤 확정한다.

지표 스냅샷은 [06_RESULT_STORAGE.md](06_RESULT_STORAGE.md)의 입력이 된다.

## 5. 사용 기술

- DuckDB SQL
- Parquet
- PostgreSQL SQL
- Python 기반 SQL 실행 순서 제어
- pytest를 이용한 지표 SQL 검증

SQL 파일은 집계 목적별로 분리하고 Python 코드 안에 긴 SQL 문자열을 중복 작성하지 않는 방향으로 설계한다.

## 6. 성공 조건

- 게임 분석 지표와 운영 지표가 구분된다.
- 모든 확정 지표에 계산식, 단위, 집계 기준, 필터가 문서화된다.
- 지표 계산에 사용한 행 수가 기록된다.
- `FAIL` 배치의 지표가 게시되지 않는다.
- 동일 입력과 지표 버전은 같은 결과를 생성한다.
- 이전 정상 배치와의 비교 기준이 일관된다.
- 작은 고정 데이터에서 예상 결과와 SQL 결과가 일치한다.
- PostgreSQL 적재에 필요한 키와 자료형이 제공된다.

## 7. 실패 가능성

- 실제 컬럼이 후보 지표 계산에 충분하지 않을 수 있다.
- 경기와 이벤트 조인에서 행이 증폭될 수 있다.
- 중복 제거 전후의 분모가 달라질 수 있다.
- 좌표 단위가 불명확해 거리 지표가 잘못 계산될 수 있다.
- 이전 정상 배치 선택이 잘못될 수 있다.
- NULL 처리에 따라 비율이 왜곡될 수 있다.
- 대규모 조인과 집계가 디스크 또는 시간을 과도하게 사용할 수 있다.
- 지표 정의 변경 후 과거 결과와 비교가 불가능할 수 있다.

## 8. 확인 및 복구

- 지표별 입력 행 수와 조인 전후 행 수를 기록한다.
- 작은 테스트 데이터로 분모, 필터, 조인 결과를 검증한다.
- 지표 버전을 저장해 정의 변경 전후 결과를 구분한다.
- 계산 실패 지표는 다른 지표의 성공 결과와 분리해 기록한다.
- SQL 실패 시 지표를 부분 게시할지 전체 중단할지 정책을 따른다.
- 잘못 게시된 지표는 해당 `run_id`와 버전으로 식별해 재계산한다.

## 9. 채용공고 요구사항과의 연결

- SQL 집계, 필터, 조인을 이용한 분석
- 게임 데이터에서 의미 있는 지표 정의
- 파이프라인 처리량과 품질 상태 모니터링
- 지표 계산 근거와 분모를 문서화하는 역량
- 정기 갱신과 이전 배치 비교를 고려한 운영 설계
- 테스트 가능한 SQL 작성

## 10. 미확정 사항

- 실제 구현 가능한 게임 분석 지표
- 지표별 컬럼과 조인 키
- 좌표 단위와 거리 계산식
- 지표별 필터와 NULL 처리
- 집계 단위와 갱신 주기
- 이전 정상 배치 선택 규칙
- 이상 변화 임계값
- 지표 SQL 파일 구조
- 부분 지표 게시 정책
- 물리 출력 스키마
