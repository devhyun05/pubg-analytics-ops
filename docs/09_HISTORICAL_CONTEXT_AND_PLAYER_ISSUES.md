# 환경 사망 집중 지역 탐지 문제 정의

## 1. 문서 목적

이 문서는 현재 보유한 PUBG 경기·사망 데이터로 직접 계산할 수 있는 분석 문제와
해석 범위를 정의한다.

기존 패치 결과를 그대로 재현하는 것을 메인 주제로 삼지 않는다. 대신 대규모
사망 이벤트에서 환경 사망이 특정 위치와 경기 시간 구간에 반복적으로 집중되는지
탐색하고, 맵 QA 또는 라이브 운영에서 추가로 점검할 후보를 만드는 것을 목표로 한다.

최종 핫스팟 분석은 아직 수행되지 않았다. 2026-07-31에 공간 집중 신호의 존재만
확인하는 일회성 예비 집계를 수행했으며 결과와 제한은
[05_SQL_METRICS.md](05_SQL_METRICS.md)에 기록했다. 실제 핫스팟 수와 최종
지표는 품질 파이프라인 실행 후 측정한 값만 기록한다.

## 2. 분석 배경

현재 데이터에는 사망 원인과 피해자 위치가 포함되어 있다. 따라서 한 번의 경기에서
우연히 발생한 사망과 여러 경기·날짜에 걸쳐 같은 위치에서 반복된 사망을 구분해
볼 수 있다.

단순히 사망 건수가 많은 위치만 찾으면 플레이어가 많이 모이는 지역이 선택될 수
있다. 따라서 사망 건수뿐 아니라 고유 경기 수, 발생 날짜 수, 해당 위치의 전체
사망 중 환경 사망 비율을 함께 확인해야 한다.

## 3. 현재 데이터 범위

### 확인된 규모

| 항목 | 확인 결과 |
|---|---:|
| 압축 해제된 CSV 전체 크기 | 약 19GB |
| aggregate 파일 수 | 5 |
| deaths 파일 수 | 5 |
| aggregate 행 수 | 67,369,231 |
| deaths 행 수 | 65,370,475 |
| deaths 고유 경기 수 | 722,425 |
| aggregate 날짜와 연결된 deaths 행 수 | 65,367,866 |
| aggregate와 연결되지 않은 deaths 행 수 | 2,609 |
| deaths 날짜 연결률 | 약 99.996% |
| aggregate 기록 시작 시각 | 2017-10-20 08:01:07 UTC |
| aggregate 기록 종료 시각 | 2018-01-10 12:02:16 UTC |

death 데이터에는 경기 날짜가 없다. 날짜 기반 분석을 위해 `match_id`로 aggregate의
`date`를 연결해야 한다. 연결되지 않은 2,609행은 날짜 기반 분석에서 제외하고,
제외 건수를 파이프라인 실행 결과에 기록한다.

위 기간은 aggregate에 기록된 경기 시각 범위다. OP.GG 수집 시각이나 Kaggle 파일
생성 시각과 동일하다고 단정하지 않는다.

## 4. 메인 분석 질문

> 에란겔과 미라마에서 `Falling`과 `Drown` 사망이 특정 위치에 여러 경기와
> 날짜에 걸쳐 반복적으로 집중되는가?

분석 결과는 실제 버그를 확정하는 것이 아니라 추가 조사가 필요한 위치와 시간
구간을 선별하는 데 사용한다. 초기 분석은 공간적 집중에만 초점을 맞추며 경기 내
시간 구간 분석은 포함하지 않는다.

## 5. 사망 원인 분류

초기 분석은 지형이나 환경 오브젝트 검토와 직접 연결할 수 있는 두 사망 원인만
대상으로 한다.

| 분류 | `killed_by` 값 | 확인된 사망 수 | 분석 목적 |
|---|---|---:|---|
| 환경 사망 | `Falling` | 708,367 | 반복 낙사 위치 탐지 |
| 환경 사망 | `Drown` | 271,712 | 반복 익사 위치 탐지 |

다음 원인은 초기 공간 분석에서 제외한다.

- `Hit by Car`는 다른 플레이어가 원인일 수 있으므로 차량 관련 사망으로 분리한다.
- `Bluezone`과 `RedZone`은 경기마다 위치가 달라지는 시스템 사망이므로 별도
  시간 분석 후보로 유지한다.
- 무기, 주먹, 수류탄 등 전투 사망은 현재 문제 정의에 포함하지 않는다.

## 6. 사용할 데이터

### deaths 핵심 입력 컬럼

| 컬럼 | 역할 |
|---|---|
| `killed_by` | `Falling`과 `Drown` 사망 분류 |
| `map` | 에란겔과 미라마 분리 |
| `match_id` | 고유 경기 반복 수 계산 및 aggregate 연결 |
| `victim_position_x` | 피해자 위치 X 격자 생성 |
| `victim_position_y` | 피해자 위치 Y 격자 생성 |

### aggregate 날짜 연결 컬럼

| 컬럼 | 역할 |
|---|---|
| `match_id` | deaths와 aggregate 연결 |
| `date` | 여러 날짜에 반복됐는지 확인 |

deaths에는 날짜가 없으므로 다음 조건으로 aggregate의 날짜를 연결한다.

```text
deaths.match_id = aggregate.match_id
```

최종 초기 분석 데이터의 최소 컬럼은 다음과 같다.

```text
match_id
date
map
killed_by
victim_position_x
victim_position_y
```

### 초기 분석에서 사용하지 않는 컬럼

| 컬럼 | 제외 이유 |
|---|---|
| `killer_name` | 환경 사망 위치 집계에 필요하지 않음 |
| `killer_placement` | 환경 사망 위치 집계에 필요하지 않음 |
| `killer_position_x` | 피해자 사망 위치만 사용 |
| `killer_position_y` | 피해자 사망 위치만 사용 |
| `victim_name` | 개인 식별 없이 경기·위치 단위로 집계 |
| `victim_placement` | 초기 공간 집중 분석에 필요하지 않음 |
| `time` | 경기 시간 구간 분석을 수행할 때만 추가 |
| `match_mode` | 초기 공간 분석 이후 세부 비교 시 추가 |
| `party_size` | 초기 공간 분석 이후 세부 비교 시 추가 |
| `game_size` | 초기 공간 분석 이후 규모 보정 검토 시 추가 |

원본 파일에서는 컬럼을 삭제하지 않는다. 분석용 조회와 집계 테이블에서만 제외한다.
특히 사용자 이름은 분석 결과와 BI 테이블에 저장하지 않는다.

### 컬럼 선택 및 필터 순서

처음부터 `Falling`과 `Drown` 행만 읽고 나머지 품질 상태를 숨기지 않는다.

1. deaths 전체에서 핵심 5개 컬럼을 선택한다.
2. 필수 컬럼의 NULL 수와 비율을 측정한다.
3. `killed_by` 전체 값과 분포를 확인한다.
4. 좌표의 형식, 범위, 이상값을 확인한다.
5. 품질 검사 결과를 기록한다.
6. 그다음 `Falling`과 `Drown` 행을 분석 대상으로 필터링한다.
7. aggregate의 `date`를 연결한다.

## 7. 분석 단위

### 원본 단위

deaths 데이터의 한 행은 한 사망 이벤트를 나타내는 것으로 가정하지 않고, 실제
샘플과 중복 후보를 먼저 확인한 뒤 이벤트 단위를 확정한다.

### 공간 단위

피해자 좌표를 일정한 크기의 격자로 나누어 `map_grid_id`를 만든다.

```text
map_grid_id = map + x_grid + y_grid
```

격자 크기는 좌표 최솟값·최댓값·분포와 맵 이미지 좌표 체계를 확인한 뒤 결정한다.
좌표 단위를 확인하기 전에는 격자를 미터 단위라고 표현하지 않는다.

맵 이미지와 좌표 변환 방식이 확인되지 않아도 원본 좌표 격자를 이용한 집계는
먼저 수행할 수 있다. 지도 위 시각화는 변환 방식 확인 후 추가한다.

### 후속 시간 분석

초기 분석에는 `time`을 사용하지 않는다. 공간 핫스팟 분석을 완료한 뒤 경기 내
사망 시간 구간이 필요하다고 판단되면 `time`의 의미와 단위를 먼저 확인하고
별도 분석으로 추가한다.

## 8. 핵심 지표

### 환경 사망 수

```text
environmental_death_count
```

특정 맵·격자·사망 원인에서 발생한 사망 이벤트 수다.

### 반복 경기 수

```text
distinct_match_count
= 환경 사망이 발생한 고유 match_id 수
```

한 경기에서 우연히 여러 번 발생한 현상과 여러 경기에서 반복된 현상을 구분한다.

### 반복 날짜 수

```text
distinct_date_count
= 환경 사망이 발생한 고유 경기 날짜 수
```

특정 하루에만 발생한 현상과 여러 날짜에 걸쳐 지속된 현상을 구분한다.

### 위치 내 환경 사망 비율

```text
environmental_death_share
= 해당 격자의 환경 사망 수 / 해당 격자의 전체 사망 수
```

사망 자체가 많은 인기 지역인지, 전체 사망 중 환경 사망의 비중이 상대적으로 높은
지역인지 구분하기 위한 보조 지표다.

이 비율의 분모는 해당 위치를 방문한 전체 플레이어 수가 아니라 해당 위치에서
발생한 전체 사망 수다. 따라서 위치별 실제 사망 확률로 해석하지 않는다.

### 전체 경기 기준 발생률

```text
environmental_deaths_per_1,000_matches
= 환경 사망 수 / 분석 대상 전체 고유 경기 수 * 1,000
```

기간이나 맵별 전체 규모가 다를 때 비교하기 위한 지표다. 이 지표 역시 해당 위치를
통과한 플레이어 수를 반영하지 않으므로 위치별 위험 확률은 아니다.

## 9. 핫스팟 선정 원칙

분석 전에 임의로 “100건 이상이면 문제”와 같은 기준을 확정하지 않는다. 먼저 전체
격자의 지표 분포를 측정하고 다음 조건을 함께 고려한다.

1. 환경 사망 수가 맵 내에서 상대적으로 높은가?
2. 충분히 많은 고유 경기에서 반복되었는가?
3. 여러 날짜에 걸쳐 반복되었는가?
4. 해당 위치의 전체 사망 중 환경 사망 비율이 높은가?
5. 한 경기 또는 하루의 극단값에 의해 만들어진 결과가 아닌가?

최종 기준은 상위 백분위와 최소 고유 경기 수를 조합한다. 기준값은 프로파일링 결과와
함께 문서화하고 변경 시 이유를 남긴다.

## 10. 결과 해석 기준

### 사용할 수 있는 표현

- 여러 경기와 날짜에 걸쳐 환경 사망이 반복된 위치
- 환경 사망 비율이 다른 격자보다 상대적으로 높은 위치
- 원인별 환경 사망 집중 위치
- 맵 QA에서 추가 확인할 수 있는 점검 후보
- 환경 사망 집중 현상을 모니터링하기 위한 운영 지표

### 사용하면 안 되는 표현

- 해당 위치에 지형 버그가 존재한다.
- 해당 위치를 방문하면 사망 확률이 높다.
- 모든 `Falling` 사망이 비정상적인 낙사다.
- 모든 `Hit by Car` 사망이 차량 물리 오류다.
- 환경 사망이 플레이어 이탈을 발생시켰다.

현재 데이터에는 플레이어 이동 경로와 위치별 방문자 수가 없다. 따라서 환경 사망
집중도는 계산할 수 있지만 위치별 노출 대비 사망 확률은 계산할 수 없다.

결과 명칭은 `위험 지역`보다 `환경 사망 집중 지역` 또는 `QA 점검 후보`를 사용한다.

## 11. 데이터 품질 확인 사항

분석 전에 다음 항목을 프로파일링한다.

1. `match_id` 결측과 형식
2. deaths와 aggregate의 `match_id` 연결률
3. 동일 경기의 aggregate `date` 일관성
4. `map` 값의 종류와 결측
5. `killed_by` 값의 공백·대소문자·알 수 없는 값
6. 피해자 좌표의 결측·최솟값·최댓값·이상값
7. 맵별 좌표 범위 차이
8. 후속 시간 분석을 수행할 경우 `time`의 의미·단위·결측·범위
9. 사망 이벤트 중복 후보
10. 전체 행 수와 실제 분석에 사용한 행 수

품질 검사에 실패한 행은 조용히 삭제하지 않는다. 제외 또는 격리한 행 수와 이유를
파이프라인 실행 이력에 기록한다.

## 12. 파이프라인 연결

```text
원본 CSV 프로파일링
→ 컬럼·좌표·사망 원인 품질 검사
→ deaths와 aggregate 날짜 연결
→ 맵별 좌표 격자 생성
→ 격자별 사망·고유 경기·고유 날짜 집계
→ 환경 사망 집중 지역 후보 생성
→ PostgreSQL 집계 테이블과 실행 이력 저장
→ Superset 히트맵·순위표 제공
→ 신규 또는 반복 핫스팟 운영 리포트 생성
```

AI는 계산이나 최종 품질 판정에 사용하지 않는다. SQL과 명시적인 규칙이 생성한
결과를 사람이 읽기 쉬운 운영 리포트로 요약하는 데만 사용한다.

## 13. 의사결정 활용 시나리오

이 분석의 가상 활용 대상은 맵 QA 또는 라이브 운영 담당자다. 실제 KRAFTON 내부
프로세스라고 주장하지 않고 공개 데이터를 이용한 포트폴리오 시나리오로 명시한다.

분석 결과는 다음 의사결정을 지원한다.

- 어떤 맵 위치를 먼저 추가 확인할 것인가?
- 어떤 사망 원인을 우선 확인할 것인가?
- 일시적인 사건과 지속적으로 반복되는 사건을 어떻게 구분할 것인가?
- 다음 데이터 배치에서도 같은 위치가 계속 탐지되는가?

### 핫스팟 탐지 후 조치 절차

환경 사망이 많은 격자가 발견됐다는 이유만으로 지형이나 오브젝트 수정을 바로
제안하지 않는다. 다음 순서로 데이터 문제, 정상적인 게임 행동과 실제 맵 문제
후보를 구분한다.

1. 동일 좌표 반복, 중복, `(0,0)`, 맵·날짜 누락 등 데이터 이상이 아닌지 확인한다.
2. 여러 격자 크기에서도 집중 현상이 유지되는지 확인한다.
3. 사망 수뿐 아니라 고유 경기 수, 고유 날짜 수, 위치 내 환경 사망 비율을 확인한다.
4. 한 경기, 하루 또는 특정 파일이 결과를 지배하지 않는지 확인한다.
5. 과거 지도 이미지에 위치를 표시해 수면, 절벽, 건물과 이동 경로의 맥락을 조사한다.
6. 상위 후보를 맵 QA가 재현하거나 추가 로그로 확인할 수 있는 점검 목록으로 만든다.
7. QA와 게임 디자인 검토에서 원인이 확인된 경우에만 수정 대안을 검토한다.
8. 수정 후 같은 지표를 다시 계산해 환경 사망의 감소와 다른 위치로의 이동 여부를
   확인한다.

점검 후보에는 다음 근거를 함께 제공한다.

| 항목 | 목적 |
|---|---|
| 맵, 격자 범위와 중심 좌표 | 재현할 위치 식별 |
| `Falling`·`Drown` 구분 | 조사할 사망 유형 식별 |
| 사망 수와 위치 내 비율 | 규모와 상대적 집중도 확인 |
| 고유 경기 수와 날짜 수 | 반복성 확인 |
| 격자 크기별 순위 | 격자 경계에 따른 결과 왜곡 확인 |
| 데이터 품질 상태 | 잘못된 좌표나 조인 결과 배제 |
| 과거 지도 확대 이미지 | 지형과 오브젝트의 초기 맥락 제공 |
| 확인된 패치 이력 | 버전 차이와 기존 변경 사항 확인 |

가능한 조치 수준은 다음처럼 구분한다.

| 상태 | 의미 |
|---|---|
| `MONITOR` | 신호는 있으나 근거가 부족해 다음 배치에서 반복 여부를 확인 |
| `QA_REVIEW` | 여러 경기와 날짜에 반복되어 게임 내 재현과 상세 로그 확인이 필요 |
| `DESIGN_REVIEW` | QA에서 지형·오브젝트 또는 이동 동선 문제가 확인돼 수정 검토 필요 |
| `DATA_ISSUE` | 좌표, 중복, 조인 또는 수집 문제로 분석 대상에서 제외 |
| `NO_ACTION` | 정상적인 플레이 패턴으로 설명돼 별도 조치 없이 종료 |

수정 대안은 원인 확인 후 결정한다. 예를 들어 낙사 후보에는 충돌, 절벽 경계,
난간, 이동 가능 경로를 확인할 수 있고, 익사 후보에는 수면 경계, 물 깊이,
육지로 나오는 경로와 충돌 상태를 확인할 수 있다. 이는 가능한 조사 항목이지
현재 데이터만으로 확정한 수정안이 아니다.

이 프로젝트의 데이터는 2017~2018년 정적 데이터이므로 실제 수정 후 신규 배치를
받아 전후 효과를 측정할 수 없다. 포트폴리오에서는 상위 후보와 QA 전달용 근거를
생성하고, 후속 측정 설계까지 제안하되 실제 조치나 개선 효과를 완료했다고
표현하지 않는다.

#### 데이터셋 동봉 지도와 좌표 확대

로컬 데이터셋에는 다음 두 참고 지도 이미지가 포함되어 있다.

| 맵 | 파일 | 해상도 | 버전 근거 |
|---|---|---:|---|
| Erangel | `data/staged/erangel.jpg` | 4096×4096 | 이미지에 `June 2017` 표시 |
| Miramar | `data/staged/miramar.jpg` | 1000×1000 | 구형 지역명 표시, 정확한 제작일 미확인 |

PUBG 공식 [Telemetry Objects 문서](https://documentation.pubg.com/en/telemetry-objects.html)는
위치 값의 단위를 cm로 설명하고, `(0,0)`을 맵의 왼쪽 위로 정의하며 Erangel과
Miramar의 X·Y 범위를 `0~816,000`으로 제시한다.

따라서 이미지 전체가 같은 좌표 범위에 정확히 정렬된다는 가정 아래 다음 후보
변환식을 사용할 수 있다.

```text
pixel_x = victim_position_x / 816000 * image_width
pixel_y = victim_position_y / 816000 * image_height
```

이 변환은 데이터셋이나 이미지 메타데이터에서 직접 제공된 공식 매핑식이 아니다.
실제 오버레이에 사용하기 전에 알려진 해안선, 도시와 도로 위치를 기준으로 방향,
여백과 스케일을 검증한다. 정렬이 확인되면 특정 좌표 주변만 잘라서 사망 원인,
격자 범위와 사망 건수를 표시할 수 있다.

Erangel 이미지의 후보 해상도는 약 1.99m/px이고 Miramar는 약 8.16m/px이다.
이는 전체 이미지가 8.16km 좌표 범위와 일치한다는 가정값이다. Erangel은 비교적
세밀한 지역 확대가 가능하지만 Miramar는 작은 오브젝트를 구분하기 어렵다.

지도 이미지에서 확인 가능한 범위:

- 해안선, 수면, 도로, 도시와 큰 건물 배치
- 산지, 절벽과 큰 지형의 대략적인 위치
- 환경 사망 격자와 기존 지형의 공간적 겹침

지도 이미지로 확인할 수 없는 범위:

- 정확한 3D 지형 높이와 `z` 좌표
- 충돌 판정, 물 깊이와 이동 가능 여부
- 울타리, 난간, 작은 바위 등 세부 오브젝트의 정확한 상태
- 해당 지형이나 오브젝트가 실제 사망 원인이었는지 여부

따라서 이 이미지는 과거 환경 사망의 위치를 이해하고 상위 후보의 확대 지도를
만드는 데 사용한다. 버그 원인 판정에는 사용하지 않는다.

따라서 과거 좌표의 현재 상태를 직접 플레이해 확인하는 작업은 메인 분석 결과의
검증이 아니라 후속 정성 조사로 분류한다. 공식 패치 노트에 특정 좌표의 수정
이력이나 수정 전후 원인이 명시되지 않았다면, 과거 핫스팟이 패치를 유발했거나
현재 해결됐다고 단정하지 않는다.

파이프라인과 핫스팟 지표가 완성된 뒤 상위 3~5개 위치에 한해 다음 절차로
현장 검토를 수행할 수 있다.

1. 과거 데이터의 맵, 격자, 사망 원인, 사망 수, 고유 경기 수와 날짜 수를 기록한다.
2. 해당 위치 또는 인접 지역이 언급된 공식 패치 노트를 확인한다.
3. 현재 게임의 패치 버전, 관찰 날짜, 게임 모드와 맵 상태를 기록한다.
4. 동일 위치를 플레이하며 지형, 수면, 절벽, 이동 경로와 엄폐물을 관찰한다.
5. 가능한 경우 동일한 시점과 방향의 스크린샷 또는 짧은 영상을 근거로 남긴다.
6. 결과를 `유사`, `변경 확인`, `위치 식별 불가`, `판단 불가`로 구분한다.

사용할 수 있는 표현:

- 과거 데이터에서 반복 환경 사망 후보가 탐지됐다.
- 공식 패치 노트에서 해당 지역 또는 인접 지역의 변경을 확인했다.
- 현재 버전 현장 관찰에서 지형 또는 오브젝트 차이를 확인했다.
- 현재 상태를 과거와 직접 비교하려면 버전별 맵 자료가 추가로 필요하다.

사용하면 안 되는 표현:

- 이 데이터 분석 때문에 해당 맵이 수정됐다.
- 현재 플레이에서 사망하지 않았으므로 과거 문제가 해결됐다.
- 동일한 X·Y 좌표는 2017년과 현재에 동일한 오브젝트를 가리킨다.
- 한 번의 플레이로 해당 위치가 안전하거나 위험하다고 검증했다.

이 후속 조사는 데이터 품질 파이프라인, 격자 집계와 대시보드 구현을 대체하지
않는다. 포트폴리오에서는 정량 분석으로 점검 후보를 선별한 뒤 공식 변경 이력과
현재 현장 관찰을 결합한 제한적 사례 연구로 제시한다.

## 14. STAR 작성 기준

### Situation

> PUBG 공개 데이터에는 에란겔과 미라마의 사망 원인과 피해자 위치가 포함되어
> 있었지만, 환경 사망이 특정 위치에 반복적으로 집중되는지를 보여주는 집계 지표는
> 제공되지 않았다. 그래서 낙사나 익사 같은 환경적 요인으로 인한 사망이 특정
> 위치에서 여러 경기와 날짜에 걸쳐 반복되는지 확인하고, 반복 빈도와 집중도가
> 높은 위치를 맵 QA 및 지형·환경 오브젝트 수정 검토 후보로 제안하고자 했다.

> 포함되어 있었습니다. 하지만 환경 사망이 특정 위치에서 반복적으로 집중되는지
> 보여주는 지표는 제공되지 않았습니다. 그래서 특정 위치에서 낙사나 익사 같은

## 16. 후속 분석 후보: 비정상 킬 거리 행동

### 상태

아이디어 검토 단계이며 현재 환경 사망 분석 범위에는 포함하지 않는다.

### 질문 후보

> 특정 플레이어가 한 무기의 일반적인 킬 거리 분포에서 크게 벗어난 킬을 여러
> 경기와 날짜에 걸쳐 반복하는가?

### 현재 데이터로 계산 가능한 신호

다음 컬럼을 이용하면 사망 시점의 killer와 victim 좌표 간 직선거리를 계산할 수
있다.

```text
killed_by
killer_name
killer_position_x
killer_position_y
victim_position_x
victim_position_y
match_id
time
```

공식 PUBG 좌표 단위가 센티미터라는 전제에서는 다음과 같이 미터 단위 거리를
계산할 수 있다.

```text
kill_distance_m
= sqrt(
    (killer_position_x - victim_position_x)^2
    + (killer_position_y - victim_position_y)^2
  ) / 100
```

계산 전에는 두 좌표의 NULL, `0,0`, 맵 범위 밖 값과 숫자 변환 실패를 제외해야
한다. 앞서 확인한 주먹 사망의 `0,0` 피해자 좌표처럼 위치 품질 문제를 처리하지
않으면 정상 플레이어가 수 km 거리에서 주먹 킬을 한 것처럼 잘못 탐지될 수 있다.

### 후보 지표

- 무기별 킬 거리 분포와 상위 백분위
- 플레이어·무기별 극단 거리 킬 수
- 극단 거리 킬이 발생한 고유 경기 수와 날짜 수
- 전체 킬 중 극단 거리 킬 비율
- deaths 킬 수와 aggregate `player_kills`의 차이
- 짧은 시간에 반복된 킬 수

한 번의 극단값으로 후보를 만들지 않는다. 무기별 기준, 최소 킬 수, 고유 경기 수와
반복 날짜를 함께 사용해야 한다.

### 현재 데이터의 한계

- 발사 이벤트와 명중 이벤트가 없다.
- 조준, 반동, 시야와 벽 관통 정보를 알 수 없다.
- 무기 부착물과 조준경 정보를 알 수 없다.
- killer와 victim의 이동 경로와 높이 좌표가 없다.
- 신고, 운영자 판정과 실제 제재 결과가 없다.
- `killer_name`은 계정 ID가 아니므로 동일인 추적을 보장하지 않는다.
- 정상·핵 라벨이 없어 탐지 정확도와 오탐률을 평가할 수 없다.

따라서 현재 데이터만으로 핵 사용자를 확정할 수 없다. 만들 수 있는 결과는
`핵 사용자 목록`이 아니라 `추가 검토가 필요한 비정상 킬 거리 행동 후보`다.

### 개인정보와 공개 원칙

- 원본 사용자 이름을 대시보드나 포트폴리오에 공개하지 않는다.
- 후보 ID는 해시 또는 비식별 값으로 변환한다.
- 특정 사용자를 핵 사용자라고 표현하지 않는다.
- 후보 생성 규칙, 좌표 제외율과 한계를 함께 공개한다.

### 범위 결정

이 아이디어는 데이터 품질 파이프라인을 재사용할 수 있는 후속 확장 후보로만
유지한다. 현재 메인 분석인 환경 사망 집중 지역 탐지와 품질 규칙을 완료한 뒤
진행 여부를 다시 결정한다.
