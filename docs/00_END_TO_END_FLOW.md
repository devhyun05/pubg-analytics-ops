# PUBG Analytics Operations 전체 흐름

> 문서 상태: 구현 결과 반영
>
> 구현 상태: 데이터 입력부터 Superset·히트맵 연결까지 구현
>
> 프로젝트 시작점: 이미 수집되어 제공되는 PUBG 원본 데이터

## 1. 목적

이 프로젝트는 PUBG 원본 데이터를 직접 수집하는 시스템이 아니라, 이미 제공된 대규모 데이터를 분석가가 안정적으로 사용할 수 있도록 만드는 분석 운영 파이프라인이다.

프로젝트는 다음 문제를 해결한다.

- 대규모 CSV의 구조와 품질을 처리 전에 파악한다.
- 반복 가능한 Python 파이프라인으로 CSV를 정제하고 Parquet으로 변환한다.
- 품질 검사를 통해 분석 가능한 데이터만 다음 단계로 전달한다.
- SQL로 게임 분석 지표와 데이터 운영 지표를 계산한다.
- PostgreSQL에 실행 이력과 집계 결과를 저장한다.
- Superset에서 데이터 상태와 분석 결과를 확인한다.
- 확정된 운영 결과를 바탕으로 AI 보고서 초안을 생성할 수 있게 한다.

현재 구현의 시작 지점은 Kaggle 데이터셋의 출처와 실제 로컬 파일 구성이
확인된 상태다. 종료 지점은 운영 담당자가 Superset에서 최신 실행 상태,
품질 결과와 공간 집중 후보를 확인하고 당시 지도 히트맵으로 실제 위치를
점검할 수 있는 상태다. AI 운영 보고서 자동 생성은 후속 범위다.

## 2. 입력

이 문서의 입력은 다음과 같다.

- 프로젝트가 증명해야 할 데이터 분석 운영 요구사항
- 프로젝트 고정 아키텍처
- Kaggle 데이터셋 `skihikingkevin/pubg-match-deaths`의 공개 메타데이터
- 데이터 다운로드 전 출처 및 라이선스 조사 결과
- 원본 데이터를 Git에 저장하지 않는 프로젝트 원칙

실제 deaths CSV 5개 65,370,475행을 확인했다. 이 중 `Falling`과 `Drown`
980,079행을 후보로 선택했고 품질 규칙과 날짜 연결을 통과한 793,356행을
최종 분석 입력으로 사용했다. 공개 데이터 전체 규모와 실제 처리 범위를
구분해 기록한다.

## 3. 처리

전체 흐름은 다음과 같다.

```text
PUBG 원본 데이터 확인
        ↓
데이터 규모·컬럼·분포 프로파일링
        ↓
Python 정제·반복 처리 자동화
        ↓
데이터 품질 검사
        ↓
SQL 지표 계산
        ↓
PostgreSQL 결과 저장
        ↓
Superset 대시보드
        ↔
당시 지도 히트맵

AI 운영 보고서 자동 생성: 미구현
```

단계별 연결 계약은 다음과 같다.

| 단계 | 입력 | 핵심 처리 | 출력 | 상세 문서 |
|---|---|---|---|---|
| 1. 데이터 출처 및 입력 | Kaggle 공개 메타데이터 | 출처, 라이선스, 파일 구성, 로컬 보관 정책 확인 | 입력 데이터 명세와 수집 승인 조건 | [01_DATA_SOURCE_AND_INPUT.md](01_DATA_SOURCE_AND_INPUT.md) |
| 2. 데이터 프로파일링 | 승인된 원본 파일과 입력 명세 | 파일, 컬럼, 타입, NULL, 고유값, 범위, 키 후보 조사 | 프로파일링 결과와 데이터 사전 초안 | [02_DATA_PROFILING.md](02_DATA_PROFILING.md) |
| 3. Python 처리 | 원본 파일과 프로파일링 결과 | 파일 탐색, 스키마 확인, 정제, Parquet 변환, 실행 이력 생성 | 정제 Parquet과 배치 실행 결과 | [03_PYTHON_PROCESSING.md](03_PYTHON_PROCESSING.md) |
| 4. 데이터 품질 | 정제 Parquet, 스키마 기준, 실행 정보 | 품질 규칙 실행과 상태 판정 | `PASS`, `WARNING`, `FAIL` 검사 결과 | [04_DATA_QUALITY.md](04_DATA_QUALITY.md) |
| 5. SQL 지표 | 품질 게이트를 통과한 Parquet과 실행 결과 | 게임 분석 및 운영 지표 집계 | 지표 스냅샷과 적재 대상 데이터 | [05_SQL_METRICS.md](05_SQL_METRICS.md) |
| 6. 결과 저장 | 지표, 품질 결과, 실행 이력 | PostgreSQL 멱등 적재와 조회용 구조 제공 | 운영 및 BI 조회 테이블 | [06_RESULT_STORAGE.md](06_RESULT_STORAGE.md) |
| 7. BI 대시보드 | PostgreSQL 집계 테이블과 뷰 | KPI, 상태 표, 공간 순위, 맵·원인 필터 구성 | `PUBG Analytics Operations`와 히트맵 링크 | [07_BI_DASHBOARD.md](07_BI_DASHBOARD.md) |
| 8. AI 보고서 | 확정된 품질 결과, 지표 이상, 실행 상태 | 후속 구현 예정 | 미구현 | [08_AI_REPORT_AUTOMATION.md](08_AI_REPORT_AUTOMATION.md) |

프로젝트에 포함하는 범위는 다음과 같다.

- 공개 데이터셋의 출처와 사용 범위 확인
- 대규모 원본 파일 프로파일링
- CSV 정제와 Parquet 변환
- 데이터 품질 검사와 이상 탐지
- SQL 기반 지표 계산
- 파이프라인 실행 이력 관리
- PostgreSQL 결과 저장
- Superset 대시보드
- 확정 결과 기반 AI 운영 보고서 설계
- 테스트, 린트, 실행 방법 및 운영 문서

## 4. 출력

이 단계의 출력은 프로젝트 전체 단계와 경계를 정의한 실행 지도와 다음 실제
산출물이다.

- `run_id`: 파이프라인 실행 식별자
- `batch_id`: 최종 Parquet 체크섬 기반 입력 묶음 식별자
- `data/processed/environmental_deaths.parquet`: 최종 분석 입력
- `analytics_ops` 스키마: 실행·품질·100m 공간 집계
- `PUBG Analytics Operations`: Superset 운영 대시보드
- `reports/environmental_death_heatmaps.html`: 당시 지도 기반 공간 리포트

`source_file_id`와 명시적인 `schema_version` 저장은 아직 구현하지 않았다.

## 5. 사용 기술

| 역할 | 기술 |
|---|---|
| 파이프라인 및 자동화 | Python 3.12 |
| 대규모 CSV 조회와 SQL 처리 | DuckDB |
| 상세 이벤트 저장 | Parquet |
| 실행 이력, 품질 결과, 집계 저장 | PostgreSQL |
| BI | Apache Superset |
| 로컬 서비스 구성 | Docker Compose |
| 테스트 | pytest |
| 정적 검사 | Ruff |
| 버전 관리와 문서화 | Git, Markdown |

## 6. 성공 조건

- 모든 단계의 입력과 출력이 문서로 연결된다.
- 원본 데이터와 집계 데이터의 저장 위치가 구분된다.
- 품질 검사 결과가 지표 게시 여부를 제어한다.
- 각 실행의 입력 행 수, 출력 행 수, 실패 수, 소요 시간이 추적된다.
- 동일 배치를 재실행해도 결과가 중복되지 않는다.
- BI와 AI가 원본 데이터의 정상 여부를 임의로 결정하지 않는다.
- 구현된 범위와 계획 상태가 문서에서 구분된다.
- 실제 처리한 행 수와 공개된 전체 데이터 규모가 구분된다.

## 7. 실패 가능성

- 공개 메타데이터와 실제 다운로드 파일 구성이 다를 수 있다.
- 파일별 스키마가 서로 다를 수 있다.
- 대규모 파일 처리 중 디스크가 부족할 수 있다.
- 일부 배치 실패 후 재실행 과정에서 중복 결과가 생길 수 있다.
- 품질 규칙이 지나치게 엄격하거나 느슨할 수 있다.
- 집계 지표가 실제 컬럼으로 계산 불가능할 수 있다.
- PostgreSQL 적재 성공과 원본 처리 성공이 불일치할 수 있다.
- 히트맵 정적 서비스가 중단되어 대시보드 링크가 열리지 않을 수 있다.
- LLM 호출 실패로 보고서 생성이 중단될 수 있다.

## 8. 확인 및 복구

- 모든 단계는 `run_id`와 상태를 기록한다.
- 실패 단계는 원인과 마지막 성공 지점을 기록한다.
- 원본 파일은 수정하지 않고 재처리 가능한 상태로 보관한다.
- `FAIL` 품질 결과가 있으면 해당 배치의 지표 게시를 중단한다.
- `WARNING`은 결과에 표시하고 정책에 따라 후속 처리를 허용한다.
- PostgreSQL 적재는 실행 식별자를 이용한 멱등 처리로 설계한다.
- `docker compose up -d --wait`로 PostgreSQL, Superset과 히트맵 서비스를
  복구한다.
- LLM 실패 시 규칙 기반 텍스트 보고서를 남긴다.
- 복구 후에는 중단된 단계부터 재실행하고 입력·출력 건수를 다시 대조한다.

## 9. 프로젝트 설계 원칙과의 연결

| 설계 원칙 | 구현 방향 |
|---|---|
| 반복 가능한 데이터 처리 | 파일 탐색, 정제, 변환, 실행 제어를 자동화한다. |
| SQL 중심의 지표 계산 | 게임 분석 지표와 데이터 운영 지표를 명시적인 SQL로 계산한다. |
| 품질 게이트 | 스키마, NULL, 중복, 참조 무결성, 데이터량 변화를 검사한다. |
| 실제 데이터 기반 스키마 | 프로파일링 결과를 바탕으로 데이터 사전과 처리 규칙을 정의한다. |
| 저장소 역할 분리 | 상세 데이터는 Parquet, 운영 및 집계 결과는 PostgreSQL에 저장한다. |
| 관측 가능한 파이프라인 | 처리 건수, 오류율, 실행 시간, 마지막 정상 갱신 시각을 추적한다. |
| 사람이 통제하는 AI | 확정된 결과만 요약하고 최종 판정과 전송은 사람이 담당한다. |
| 재현 가능한 운영 | 단계별 문서, 실행 방법, 의사결정과 버전을 함께 관리한다. |

## 10. 남은 사항

- AI 운영 보고서 자동 생성과 실행 이력
- Superset 조회 전용 계정과 권한 분리
- 플레이어 방문량을 사용한 위치별 위험률
- 새 Superset 메타데이터 볼륨의 대시보드 자동 재구성
- 공개 배포 여부와 사용할 LLM 제공자·비용 한도
